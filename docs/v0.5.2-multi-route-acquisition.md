## 1. Goal

v0.5 turns full-text acquisition from a URL-download operation into a bounded, auditable scientific-object workflow:

```text
DOI
↓
Discovery + optional Metadata
↓
FullTextCandidate[]
↓
Direct files first
↓
Route Resolution when needed
↓
Derived file candidates
↓
File retrieval
↓
PDF structure validation
↓
Paper identity validation
↓
Document-role validation
↓
VERIFIED main article
or explicit non-success + complete attempt history
```

Governing rule:

> **Only Validation can create `VERIFIED`.**

---

## 2. Layer boundaries

```text
v0.4    Discovery
        Where might full text exist?

v0.5.0  Direct Acquisition + Validation
        Is this concrete file safely retrievable and really the target main article?

v0.5.1  Route Resolution
        Can this page/resolver/repository expose trustworthy file candidates?

v0.5.2  Multi-route Orchestration
        Which route should be tried next, and when should the workflow stop?
```

v0.5 intentionally does **not** own:

- CARSI / SSO / institutional authentication;
- browser JavaScript execution or persistent browser sessions;
- CAPTCHA or anti-bot circumvention;
- paywall bypass;
- publisher-specific guessed PDF URL templates;
- uncontrolled crawling;
- OCR or scientific-content parsing;
- knowledge-base / Agent logic.

These are separate capability layers, not hidden unfinished behavior.

---

## 3. Core invariants

```text
Candidate ≠ File
File ≠ Valid PDF
Valid PDF ≠ Target Paper
Target Paper ≠ Main Article
Derived Candidate ≠ Verified File
Many attempted routes ≠ Success
```

Consequences:

- HTTP success status is not proof of a paper;
- `.pdf` in a URL is not proof of PDF content;
- a valid PDF with the wrong DOI is not success;
- supplementary or auxiliary files cannot become the verified main article;
- an access/challenge page is not a discovery failure;
- failed acquisition remains useful when provenance and failure reason are preserved.

## 4. Public API and stable defaults

### DOI-level workflow

```python
from aletheia_nexus.acquire.fulltext import acquire_full_text

result = acquire_full_text(
    "10.1038/s41893-022-00870-3",
    output_dir="downloads",
    unpaywall_email="you@example.com",
)
```

### Existing Discovery result

```python
from aletheia_nexus.acquire.fulltext import acquire_from_discovery

result = acquire_from_discovery(
    discovery,
    output_dir="downloads",
    expected_title="Known article title",
)
```

### Stable orchestration defaults

```text
max route attempts              16
max file attempts               24
max route depth                  2
max route expansions per page    4
HTTPS probe timeout              5 s
```

All network work is bounded. `max_route_expansions_per_page` is a positive integer when explicitly supplied; `max_route_depth` is non-negative.

## 5. Final workflow statuses

```text
VERIFIED
NO_CANDIDATES
DISCOVERY_FAILED
AUTH_REQUIRED
ACCESS_BLOCKED
EXHAUSTED
LIMIT_REACHED
```

Semantics:

- `VERIFIED` — target main article passed file, identity and role validation;
- `NO_CANDIDATES` — no concrete main-article file candidate became available;
- `DISCOVERY_FAILED` — discovery failed and no usable fallback recovered the workflow;
- `AUTH_REQUIRED` — terminal evidence explicitly indicates authentication/access requirements;
- `ACCESS_BLOCKED` — terminal evidence is an access block such as HTTP 403, challenge page or WAF behavior;
- `EXHAUSTED` — available routes/files were tried without verification;
- `LIMIT_REACHED` — an explicit request/depth budget stopped work first.

Conservative HTTP semantics include:

```text
401 → AUTH_REQUIRED
403 → ACCESS_BLOCKED
```

Explicit anti-bot/WAF challenge language is also classified as an access boundary rather than silently collapsing to `NO_CANDIDATES`. v0.5 records such barriers; it does not execute or bypass their challenge logic.

## 6. Route and file policy

### 6.1 Direct files first

Provider-reported PDF candidates are attempted before page routes because they are cheaper and more concrete. They still pass the complete validation chain.

### 6.2 Generic Route Resolution

Trusted generic evidence includes:

```text
citation_pdf_url / scholarly PDF metadata
<link type="application/pdf">
semantic Download/View PDF anchors
iframe / embed / object PDF routes
JSON-LD media routes
explicit PDF-looking URLs
relative URL + <base href>
explicit quoted .pdf paths in static inline script state
```

Static inline `<script>` state may expose a literal PDF URL/path. v0.5 may extract that explicit route because the page already supplied it. It does not execute JavaScript, inspect external bundles or synthesize publisher-specific paths.

### 6.3 URL derivation and safety

HTTP→HTTPS is represented as a provenance-bearing derivation rather than silent normalization. Shared URL helpers own relative resolution, fragment removal, default-port normalization, credential rejection and traceable HTTPS alternatives so multiple layers do not maintain drifting copies of the same rule.

### 6.4 Adaptive page expansion

Page expansion follows only bounded, explainable next-hop signals such as redirect targets, meta refresh, citation/public HTML metadata, canonical article links, article JSON-LD, semantic article/full-text anchors and filtered target-DOI anchors.

Weak DOI-bearing links are filtered against obvious non-article utilities such as advertisements, citation exports, Crossmark, permissions/copyright and metrics routes.

Expansion and invalid-PDF→page fallback obey the same `max_route_depth` boundary.

### 6.5 DOI resolver fallback

When provider routes fail, v0.5 can use:

```text
https://doi.org/<doi>
```

as a generic fallback. Its provenance is explicitly marked as an AN fallback, not attributed to a Discovery provider.

## 7. Identity and document role

Page identity is conservative:

```text
MATCH
MISMATCH
UNKNOWN
```

Evidence precedence:

1. exact target DOI metadata → `MATCH`;
2. explicit scholarly DOI metadata for another work → `MISMATCH`;
3. strong title similarity is fallback evidence only when DOI metadata is absent;
4. weak or missing evidence → `UNKNOWN`.

Therefore a matching-looking title cannot override explicit conflicting DOI metadata.

Document roles are:

```text
ARTICLE
SUPPLEMENT
UNKNOWN
```

`SUPPLEMENT` is also the conservative non-main role for clearly auxiliary scientific PDFs, including strong signals such as Reporting Summary, peer-review files, Source Data, decision/editorial letters, author checklists and reviewer comments.

Route-level role hints may save unnecessary downloads, but they never create `VERIFIED`. File-level validation remains final authority.

## 8. Retrieval, safety and provenance

Page transport and direct-file transport remain separate because their response handling differs, but they share small HTTP primitives for bounded parameter validation, stable User-Agent construction, redirect status definitions and HTTP-status→acquisition-error mapping.

Safety boundaries include:

- HTTP(S) only;
- hostname required;
- embedded credentials rejected;
- obvious local/private/link-local/reserved targets rejected where determinable;
- redirect targets revalidated manually;
- bounded redirects, timeouts, page/file sizes, retries and route depth;
- transient retry only for appropriate network/rate-limit/service failures.

DNS checks are a best-effort preflight defense, not a claim of adversarial DNS-rebinding-proof isolation.

The workflow preserves route and file attempt provenance, derivation evidence, parent URLs, depth and terminal status. Verified files use deterministic DOI/hash-derived filenames and an `.acquisition.json` sidecar containing retrieval, redirect, hash, PDF, identity, role and timing evidence.

Temporary partial files are cleaned on failure. Human-in-the-loop retention of unverified files remains optional.

---

## 9. Concurrency

Concurrency is deliberately narrow:

```text
Metadata lookup ┐
                ├─ concurrent bootstrap when title is absent
Discovery       ┘
```

Route/file acquisition remains adaptive and mostly sequential. Broad parallel retrieval would increase request volume, duplicate work and weaken first-success stopping without demonstrated benefit.

## 11. Real-network acceptance

Live publisher networks are intentionally **not** deterministic CI dependencies.

Fixed corpora:

```text
benchmarks/cdi_acquisition_10.json
benchmarks/seawater_desalination_10.json
```

Runner:

```text
scripts/manual_multiroute_acceptance.py
```

A same-environment 20-paper stress run on 2026-09-17 produced:

```text
CDI                         4 / 10 VERIFIED
Seawater desalination       2 / 10 VERIFIED
------------------------------------------------
Combined                    6 / 20 = 30%
```

The run was deliberately difficult and is **not** a universal paper-download success estimate. No false `VERIFIED` was observed. Route/file work was reproducible across repeated runs, while wall-clock time varied with third-party network latency.

The dominant remaining limitation was access-layer blocking: many correct routes were found but ordinary unauthenticated HTTP retrieval was rejected or intercepted by publisher/index infrastructure. A later narrow challenge-classification hardening improved failure semantics without changing acquisition success behavior; the full 20-paper corpus was not rerun solely to rewrite historical status counts.

The release criterion is correctness, explicit failure and provenance—not maximizing this small live score.

## 12. Final audit decisions

The final v0.5 audit favored deletion and consolidation over new features.

Accepted:

- shared small HTTP policy helpers instead of duplicated transport policy;
- shared derived-URL/HTTPS logic instead of drifting implementations;
- explicit conflicting DOI outranks title similarity;
- invalid-PDF page fallback obeys the route-depth budget;
- orchestration option contracts match implementation constraints;
- temporary catch-all audit tests were moved into durable module-focused tests;
- generic static inline-script PDF route extraction;
- generic anti-bot/WAF challenge recognition as `ACCESS_BLOCKED`;
- README and this file separated into project entry point vs canonical contract to reduce duplicated current-state documentation.

Explicitly rejected as unnecessary complexity:

- a universal transport class combining page and file behavior;
- publisher-specific adapters or guessed PDF templates;
- broader crawling;
- browser/authentication logic inside the HTTP core;
- wider concurrency without measured need;
- further abstraction of role/identity heuristics whose evidence semantics intentionally differ by layer.

The result is a smaller policy surface with clearer ownership rather than a more elaborate architecture.

## 13. Freeze decision

v0.5 provides the complete unauthenticated HTTP acquisition chain:

```text
Discovery
→ Route Resolution
→ Direct Acquisition
→ PDF Validation
→ Paper Identity
→ Document Role
→ Multi-route Orchestration
→ explicit terminal outcome
```

Remaining major real-world gaps predominantly belong to a different capability layer: browser/session/authenticated access. They should not be solved by contaminating the stable v0.5 HTTP core.

The next main development line is:

```text
Verified local article
↓
Content Parsing（内容解析）
↓
structured scientific document
↓
Knowledge / Workflow / Agent
```

> **v0.5 is frozen. Reopen this layer only when a reproducible correctness defect or clearly measured acquisition gap justifies the added complexity.**
