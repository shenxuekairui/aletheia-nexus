# v0.5.2 Multi-route Acquisition

> Aletheia Nexus v0.5.2 coordinates Discovery, Route Resolution, Direct Acquisition and Validation into one bounded, auditable DOI-level workflow.

**Version:** 0.5.2  
**Layer:** Multi-route Acquisition（多路径获取编排）  
**Status:** FINALIZED / FROZEN FOR MERGE

## 1. Goal

The stable primitives before v0.5.2 answer separate questions:

```text
v0.4    Discovery
        Where might full text exist?

v0.5.0  Direct PDF Acquisition + Validation
        Given one concrete file candidate, can AN retrieve it safely and verify it?

v0.5.1  Route Resolution
        Given one landing/repository/resolver route, can AN derive explainable file candidates?
```

v0.5.2 owns the coordination problem:

```text
DOI
↓
Metadata + Discovery
↓
prioritized provider candidates
↓
try concrete files first
↓
resolve page routes only when needed
↓
validate every derived file immediately
↓
expand useful next-hop routes within strict budgets
↓
first VERIFIED main article stops
↓
otherwise return an explicit terminal status + complete attempt history
```

The central invariant is:

> **Orchestration may choose what to try next, but only Validation can create VERIFIED.**

## 2. Architectural boundary

The v0.5 acquisition line is now complete for its intended unauthenticated HTTP scope:

```text
Discovery Candidate[]
        ↓
┌─────────────────────────────────────────────────┐
│ v0.5.2 Multi-route Acquisition                  │
│                                                 │
│ concrete PDF ────────────────┐                  │
│                              ↓                  │
│ page / resolver / repo       │                  │
│          ↓                   │                  │
│ v0.5.1 Route Resolution      │                  │
│          ↓                   │                  │
│ DerivedFullTextCandidate ────┘                  │
│          ↓                                      │
│ v0.5.0 Direct Acquisition + Validation          │
│          ↓                                      │
│ VERIFIED? ─ yes → stop                         │
│     │                                           │
│     no → bounded fallback / expansion           │
└─────┼───────────────────────────────────────────┘
      ↓
explicit non-success + traceable attempt history
```

v0.5.2 does **not** absorb browser automation, authentication, publisher-specific URL guessing or content parsing. Those remain separate capabilities so the stable HTTP acquisition core stays understandable and testable.

## 3. Public API

### DOI-level workflow

```python
from aletheia_nexus.acquire.fulltext import acquire_full_text

result = acquire_full_text(
    "10.1038/s41893-022-00870-3",
    output_dir="downloads",
    unpaywall_email="you@example.com",
)

print(result.status)
print(result.verified_result)
```

`acquire_full_text(...)` is the main v0.5.2 entry point. When an expected title is not supplied, Metadata Resolution and Discovery are started concurrently. A recovered metadata title is then used as validation evidence.

### Reuse an existing Discovery result

```python
from aletheia_nexus.acquire.fulltext import acquire_from_discovery

result = acquire_from_discovery(
    discovery,
    output_dir="downloads",
    expected_title="Known article title",
)
```

This entry point avoids repeating Discovery when a caller already has a `DiscoveryResult`.

## 4. Result contract

`MultiRouteAcquisitionResult` preserves both the final outcome and how AN reached it:

```text
doi
status
discovery
route_attempts
file_attempts
verified_result
metadata
metadata_error
expected_title
title_source
duplicate_file_candidates_skipped
duplicate_route_candidates_skipped
supplement_candidates_skipped
page_route_attempts
route_expansions_enqueued
max_route_depth_reached
elapsed_seconds
message
```

This is deliberately more than a `Path | None` return value. A failed acquisition is still useful evidence when it says exactly what was discovered, attempted, rejected or blocked.

### Attempt provenance

Every route attempt records:

```text
candidate
origin
depth
parent_url
expansion_method
evidence
resolution result
```

Every file attempt records:

```text
candidate
origin
parent_url
derivation_method
role_hint
evidence
acquisition result
```

The system therefore keeps provider provenance and AN-derived provenance separate instead of silently rewriting history.

## 5. Final statuses

```text
VERIFIED
NO_CANDIDATES
DISCOVERY_FAILED
AUTH_REQUIRED
ACCESS_BLOCKED
EXHAUSTED
LIMIT_REACHED
```

Important semantics:

- `VERIFIED` means a target main article passed v0.5.0 validation.
- `NO_CANDIDATES` means no concrete main-article file candidate became available.
- `DISCOVERY_FAILED` is reserved for discovery-level failure when no usable fallback exists.
- `AUTH_REQUIRED` / `ACCESS_BLOCKED` are preserved only when the terminal evidence is exclusively an access boundary; mixed failures are not overinterpreted.
- `EXHAUSTED` means available candidates were tried without verification.
- `LIMIT_REACHED` means an explicit request budget stopped the search before the available search space was exhausted.

A 403 response is still `ACCESS_BLOCKED`, not automatically “institutional login required”.

## 6. Acquisition policy

### 6.1 Concrete files first

Provider-reported `PDF` candidates are cheaper and more direct than page routes, so they are attempted first.

A failed direct candidate does not become success merely because a provider labelled it PDF. It still passes the full v0.5.0 retrieval and validation contract.

### 6.2 Page routes are prioritized, not blindly exhausted

Current route priority favors useful evidence:

```text
OPEN_ACCESS
+
repository / publisher hosts
+
published / accepted versions
+
provider best-location hint
+
HTTPS
```

This is an acquisition-order policy, not a claim of scholarly authority.

### 6.3 Derived files are validated immediately

When v0.5.1 derives one or more file candidates from a page, v0.5.2 does not first crawl every remaining route. It tries the new files immediately and stops on the first trustworthy main article.

This keeps network cost bounded and makes the policy easy to explain.

### 6.4 Adaptive route expansion

If a resolved page exposes a useful next-hop page rather than a file, v0.5.2 may enqueue that route. Expansion is bounded by depth and per-page candidate limits.

The orchestration layer therefore supports realistic chains such as:

```text
DOI resolver
→ publisher/repository landing page
→ document page
→ PDF
```

without becoming an unrestricted web crawler.

### 6.5 DOI resolver fallback

If provider routes do not yield a verified file, v0.5.2 can use the standard DOI resolver as a final generic fallback:

```text
https://doi.org/<doi>
```

The resolver fallback is explicitly marked as AN fallback provenance rather than pretending that a Discovery provider supplied it.

### 6.6 HTTP → HTTPS handling

Legacy HTTP routes receive a traceable HTTPS alternative before the original route is attempted where appropriate.

This is derivation, not silent normalization:

```text
origin = URL_TRANSFORM / PDF_TRANSFORM
parent_url = original HTTP URL
method = HTTPS_UPGRADE
```

The short HTTPS probe is bounded separately so an unreachable upgrade does not consume the full route timeout.

### 6.7 Page-like “PDF” fallback

Some provider-labelled PDF URLs actually return HTML or redirect to a landing page. When the response is page-like, v0.5.2 can return that final page to Route Resolution instead of permanently treating it as a dead file candidate.

This handles stale provider metadata without weakening PDF validation.

## 7. Deduplication

Network work is deduplicated with canonical URL keys.

v0.5.2 separately tracks:

```text
duplicate_file_candidates_skipped
duplicate_route_candidates_skipped
```

Redirect destinations are also remembered, preventing a provider route and a later derived route from repeatedly resolving the same page.

Deduplication is an optimization only; it must not erase attempt provenance already observed.

## 8. Document-role policy

Strong `SUPPLEMENT` hints from Route Resolution are skipped by default at orchestration time.

This is intentionally asymmetric:

- strong supplement evidence may save a clearly unnecessary retrieval;
- ARTICLE/UNKNOWN hints never create `VERIFIED`;
- final authority remains v0.5.0 file validation.

The caller can disable supplement-hint skipping when investigating unusual cases.

## 9. Request budgets and stop conditions

Default orchestration limits:

```text
max route attempts              16
max file attempts               24
max route depth                  2
max route expansions per page    4
HTTPS probe timeout              5 s
```

These are safety and cost controls, not hidden success criteria.

The workflow stops when:

```text
1. a VERIFIED main article is obtained; or
2. a configured route/file budget is reached; or
3. no usable candidate remains.
```

There is no unbounded recursive crawl and no background retry loop.

## 10. Concurrency policy

v0.5.2 deliberately uses only narrow bootstrap concurrency:

```text
Metadata lookup  ┐
                 ├─ run concurrently when no title was supplied
Discovery        ┘
```

Route and file acquisition remains adaptive and mostly sequential because later decisions depend on earlier evidence. Parallelizing all candidate retrievals would increase request volume, duplicate work and make first-success stopping less effective.

The release audit did not show a need for broader concurrency, so no additional complexity was added.

## 12. Real-network acceptance

Live publisher networks are **not** deterministic CI dependencies. v0.5.2 therefore keeps real-network testing as an explicit release/diagnostic workflow using fixed corpora.

Current fixed corpora:

```text
benchmarks/cdi_acquisition_10.json
benchmarks/seawater_desalination_10.json
```

Runner:

```text
scripts/manual_multiroute_acceptance.py
```

Example:

```powershell
python scripts/manual_multiroute_acceptance.py `
  --corpus benchmarks/seawater_desalination_10.json `
  --output-dir real_network_acceptance/v0.5.2-seawater
```

The runner records:

```text
provider outcomes
route attempts
route depth / expansion method
file attempts
final URLs
network attempt counts
deduplication counters
role hints
elapsed time
final status counts
verified URL when available
```

A recorded seawater-desalination acceptance sample produced 2/10 `VERIFIED`, with the remaining cases expressed as explicit `ACCESS_BLOCKED`, `EXHAUSTED` or `NO_CANDIDATES` outcomes. This low raw success count is not treated as a reason to guess publisher URLs or weaken validation: the key release property is that inaccessible/uncertain routes fail explicitly and **no wrong file is promoted to `VERIFIED`**.

Live results can vary by date, runner IP and third-party request policy. Therefore a fixed live corpus is evidence about reality, while deterministic tests remain the reproducible regression gate.

The temporary GitHub Actions workflow used during v0.5.2 acceptance is removed before merge so external site changes cannot make normal CI flaky.

## 13. Accepted non-goals

v0.5.2 intentionally does not implement:

- CARSI / SSO / institutional authentication;
- browser JavaScript execution;
- cookie/session persistence;
- CAPTCHA or anti-bot circumvention;
- paywall bypass;
- publisher-specific URL template catalogues;
- guessed PDF URL synthesis;
- uncontrolled web crawling;
- OCR or scientific-content parsing;
- literature knowledge-base construction;
- an autonomous research Agent.

These exclusions are architectural boundaries, not unfinished hidden behavior.

## 14. Why v0.5 stops here

The v0.5 line now has a complete responsibility chain:

```text
route discovery
→ route resolution
→ file acquisition
→ structural validation
→ paper identity
→ document role
→ multi-route coordination
→ explicit terminal outcome
```

The remaining real-network gaps are dominated by capabilities from a **different layer**: authenticated/browser access or later scientific-content processing.

Adding more publisher-specific heuristics to the orchestration core solely to improve a 10-paper score would increase maintenance cost and make provenance weaker. The project therefore freezes v0.5.2 once its general mechanisms, failure semantics and regression suite are stable.

This follows the project rule:

> When a module is sufficiently stable, stop refactoring without evidence and invest in the next valuable layer.

## 15. Next layer

With v0.5 frozen, the next major line should move from “getting the trustworthy paper” to “turning the trustworthy paper into usable scientific information”.

A natural next boundary is:

```text
Verified local article
↓
Content Parsing（内容解析）
↓
structured text / sections / tables / figures / references
↓
traceable scientific objects
↓
Knowledge / Workflow / Agent
```

Authenticated/browser acquisition can remain a separate later capability and should only be introduced when a concrete access workflow justifies the additional state, security and maintenance complexity.
