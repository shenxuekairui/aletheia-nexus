## 1. Goal

v0.5 turns full-text acquisition from a URL download operation into a bounded, auditable scientific-object workflow:

```text
DOI
↓
Discovery + optional Metadata
↓
FullTextCandidate[]
↓
Direct files first
↓
Route Resolution when needed
↓
Derived file candidates
↓
File retrieval
↓
PDF structure validation
↓
Paper identity validation
↓
Document-role validation
↓
VERIFIED main article
or explicit non-success + complete attempt history
```

The governing rule is:

> **Only Validation can create `VERIFIED`.**

---

## 2. Layer boundaries

```text
v0.4    Discovery
        Where might full text exist?

v0.5.0  Direct Acquisition + Validation
        Is this concrete file safely retrievable and really the target main article?

v0.5.1  Route Resolution
        Can this page/resolver/repository expose trustworthy file candidates?

v0.5.2  Multi-route Orchestration
        Which route should be tried next, and when should the workflow stop?
```

v0.5 intentionally does **not** own:

- CARSI / SSO / institutional authentication;
- browser JavaScript execution or persistent browser sessions;
- CAPTCHA or anti-bot circumvention;
- paywall bypass;
- publisher-specific guessed PDF URL templates;
- uncontrolled crawling;
- OCR or scientific-content parsing;
- knowledge-base / Agent logic.

These are separate capability layers, not hidden unfinished behavior.

---

## 3. Core invariants

```text
Candidate ≠ File
File ≠ Valid PDF
Valid PDF ≠ Target Paper
Target Paper ≠ Main Article
Derived Candidate ≠ Verified File
Many attempted routes ≠ Success
```

Consequences:

- HTTP 200 is not success by itself;
- `.pdf` in a URL is not proof of PDF content;
- a valid PDF with the wrong DOI is not success;
- supplementary / auxiliary files cannot become the verified main article;
- failed acquisition remains useful when provenance and failure reason are preserved.

## 4. Public API

### DOI-level workflow

```python
from aletheia_nexus.acquire.fulltext import acquire_full_text

result = acquire_full_text(
    "10.1038/s41893-022-00870-3",
    output_dir="downloads",
    unpaywall_email="you@example.com",
)
```

### Reuse an existing Discovery result

```python
from aletheia_nexus.acquire.fulltext import acquire_from_discovery

result = acquire_from_discovery(
    discovery,
    output_dir="downloads",
    expected_title="Known article title",
)
```

### Stable orchestration defaults

```text
max route attempts              16
max file attempts               24
max route depth                  2
max route expansions per page    4
HTTPS probe timeout              5 s
```

All network work is bounded. `max_route_expansions_per_page` is a required positive integer when explicitly supplied; `max_route_depth` is a non-negative integer.

## 5. Final workflow statuses

```text
VERIFIED
NO_CANDIDATES
DISCOVERY_FAILED
AUTH_REQUIRED
ACCESS_BLOCKED
EXHAUSTED
LIMIT_REACHED
```

Important semantics:

- `VERIFIED` — target main article passed file, identity and role validation;
- `NO_CANDIDATES` — no concrete main-article file candidate became available;
- `DISCOVERY_FAILED` — discovery failed and no usable fallback recovered the workflow;
- `AUTH_REQUIRED` — terminal evidence explicitly indicates an authentication/access boundary;
- `ACCESS_BLOCKED` — terminal evidence is an access block such as HTTP 403/challenge/WAF behavior;
- `EXHAUSTED` — available routes/files were tried without verification;
- `LIMIT_REACHED` — an explicit request/depth budget stopped work first.

HTTP semantics remain conservative:

```text
401 → AUTH_REQUIRED
403 → ACCESS_BLOCKED
```

A 403 does not independently prove that institutional login is required.

## 6. Route and file policy

### 6.1 Direct files first

Provider-reported PDF candidates are attempted before page routes because they are cheaper and more concrete. They still pass the complete v0.5.0 validation chain.

### 6.2 Generic Route Resolution

Trusted generic evidence includes:

```text
citation_pdf_url / scholarly PDF metadata
<link type="application/pdf">
semantic Download/View PDF anchors
iframe / embed / object PDF routes
JSON-LD media routes
explicit PDF-looking URLs
relative URL + <base href> resolution
```

Static inline `<script>` state can also expose an **explicit quoted `.pdf` URL/path**. v0.5 may extract that literal route because the page already supplied it. It does not execute JavaScript, inspect external bundles, or synthesize publisher-specific paths.

### 6.3 Explicit HTTP → HTTPS derivation

HTTP→HTTPS is represented as provenance-bearing derivation, not silent normalization. The original route remains observable.

Shared URL helpers now own relative resolution, fragment removal, default-port normalization, credential rejection and traceable HTTPS alternatives so Route Resolution and orchestration do not maintain drifting copies of the same rule.

### 6.4 Adaptive page expansion

Page expansion follows only bounded, explainable next-hop signals such as:

```text
redirect target
meta refresh
citation/public HTML metadata
canonical article link
article JSON-LD
semantic article/full-text anchor
filtered target-DOI anchor
```

Weak DOI-bearing links are filtered against obvious non-article utilities such as advertisements, citation exports, Crossmark, permissions/copyright and metrics routes.

Expansion and page-like invalid-PDF fallback both obey the same `max_route_depth` boundary. No fallback path may silently exceed the configured depth.

### 6.5 DOI resolver fallback

When provider routes fail, v0.5 can use:

```text
https://doi.org/<doi>
```

as a final generic fallback. Its provenance is explicitly marked as an AN fallback, not attributed to a Discovery provider.

## 7. Identity and document role

Page identity is conservative:

```text
MATCH
MISMATCH
UNKNOWN
```

Evidence precedence is intentional:

1. exact target DOI metadata → `MATCH`;
2. explicit scholarly DOI metadata for another work → `MISMATCH`;
3. strong title similarity is fallback evidence only when DOI metadata is absent;
4. weak or missing evidence → `UNKNOWN`.

Therefore an exact-looking title can no longer override explicit conflicting DOI metadata.

Document roles are:

```text
ARTICLE
SUPPLEMENT
UNKNOWN
```

`SUPPLEMENT` is the conservative non-main role for conventional Supporting Information and clearly auxiliary scientific PDFs, including strong signals such as:

```text
Reporting Summary
Peer Review files
Source Data files
Decision / editorial letters
Author checklists
Reviewer comments
```

Route-level role hints may save unnecessary downloads, but they never create `VERIFIED`. File-level validation remains final authority.

## 8. Retrieval and safety

The direct-file and page transports intentionally remain separate because they have different response handling, but now share small HTTP primitives for:

- bounded parameter validation;
- stable User-Agent construction;
- redirect status definitions;
- HTTP status → acquisition error mapping.

This removes duplicated policy without creating a large generic transport abstraction.

Safety boundaries include:

- HTTP(S) only;
- hostname required;
- embedded credentials rejected;
- obvious local/private/link-local/reserved targets rejected where determinable;
- redirect targets revalidated manually;
- bounded redirects, timeouts, page/file sizes and retries;
- transient retry only for appropriate network/rate-limit/service failures.

DNS checks are a best-effort preflight defense, not a claim of adversarial DNS-rebinding-proof isolation.

## 9. Provenance and storage

The workflow keeps both final outcome and attempt history.

Route attempts preserve:

```text
candidate
origin
depth
parent URL
expansion method
evidence
resolution result
```

File attempts preserve:

```text
candidate
origin
parent URL
derivation method
role hint
evidence
acquisition result
```

Verified files use deterministic DOI/hash-derived filenames and an `.acquisition.json` sidecar containing retrieval, redirect, hash, PDF, identity, role and timing evidence.

Temporary partial files are cleaned on failure. Human-in-the-loop retention of unverified files remains optional.

---

## 10. Concurrency

Concurrency is deliberately narrow:

```text
Metadata lookup ┐
                ├─ concurrent bootstrap when title is absent
Discovery       ┘
```

Route/file acquisition remains adaptive and mostly sequential. Broad parallel retrieval would increase request volume, duplicate work and weaken first-success stopping without demonstrated benefit.

## 12. Real-network acceptance

Live publisher networks are intentionally **not** deterministic CI dependencies.

Fixed corpora:

```text
benchmarks/cdi_acquisition_10.json
benchmarks/seawater_desalination_10.json
```

Runner:

```text
scripts/manual_multiroute_acceptance.py
```

The same-environment local stress run on 2026-09-17 produced:

```text
CDI                         4 / 10 VERIFIED
Seawater desalination       2 / 10 VERIFIED
------------------------------------------------
Combined                    6 / 20 = 30%

ACCESS_BLOCKED              8
NO_CANDIDATES               4
EXHAUSTED                   2
```

This is a deliberately difficult stress corpus, **not** a universal paper-download success rate. The dominant observed limitation was access-layer blocking: many correct routes were found but ordinary unauthenticated HTTP retrieval was rejected by publisher/index infrastructure.

The release criterion is not maximizing this small live score. It is preserving correctness, explicit failure and provenance without false `VERIFIED` results.

## 13. Final audit decisions

The final v0.5 audit intentionally favored deletion and consolidation over new features.

Accepted changes:

- shared small HTTP policy helpers instead of duplicated transport policy;
- shared derived-URL / HTTPS logic instead of drifting route implementations;
- explicit conflicting DOI now outranks title similarity;
- invalid-PDF page fallback now obeys the same route-depth budget as ordinary expansion;
- `max_route_expansions_per_page` API contract now matches its positive-integer implementation;
- temporary catch-all audit tests were moved into durable module-focused regression tests;
- IEEE diagnosis produced one generic capability only: literal inline-script PDF route extraction.

Explicitly rejected as unnecessary complexity:

- a universal transport class combining page and file behavior;
- publisher-specific adapters or guessed PDF templates;
- broader crawling;
- browser/authentication logic inside the HTTP core;
- wider concurrency without measured need;
- further abstraction of role/identity heuristics whose evidence semantics intentionally differ by layer.

The result is a smaller policy surface with clearer ownership rather than a more elaborate architecture.

---

## 14. Freeze decision

v0.5 now provides the complete unauthenticated HTTP acquisition chain:

```text
Discovery
→ Route Resolution
→ Direct Acquisition
→ PDF Validation
→ Paper Identity
→ Document Role
→ Multi-route Orchestration
→ explicit terminal outcome
```

Remaining major real-world gaps predominantly belong to a different capability layer: browser/session/authenticated access. They should not be solved by contaminating the stable v0.5 HTTP core.

The next main development line is therefore:

```text
Verified local article
↓
Content Parsing（内容解析）
↓
structured scientific document
↓
Knowledge / Workflow / Agent
```

> **v0.5 is frozen. New work should reopen this layer only when a reproducible correctness defect or clearly measured acquisition gap justifies the complexity.**
