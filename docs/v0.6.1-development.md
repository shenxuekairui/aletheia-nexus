# v0.6.1 development and release gate

This document tracks work **after** the immutable `v0.6.0` tag. Development used `0.6.1.dev0`; the release candidate declares `0.6.1`. Neither a version string nor a GitHub Release proves PyPI availability: verify the upload and a fresh installation.

## Architecture boundary

- `browser.py` owns the persistent session lifecycle and source-route budget.
- `browser_route.py` remains the route orchestration and evidence-collection coordinator. It delegates publisher-specific decisions to `publisher_adapters/` and publisher-neutral native download/PDF-viewer capture to `browser_engine/`.
- `publisher_adapters/base.py` defines narrow hooks for a canonical PDF candidate, challenge refinement, article-control readiness, institution-control preference, remembered institution state, and non-PDF entitlement signals. The registry selects by exact HTTPS host (and DOI prefix only for an applicable DOI resolver). Unknown hosts use the generic adapter.
- ACS, Wiley, Taylor & Francis, ASCE, Nature, MDPI, Thieme, and IEEE rules live behind adapter implementations. Route URLs remain *candidates*; the shared PDF structure, article identity, main-text role, and provenance validation remain mandatory for every adapter.
- `publisher_routes.py` and the existing private helper names are compatibility facades for the v0.6 test surface. They should be removed only with a separately documented compatibility decision.

This is an incremental split, not a claim that the route coordinator is small. Future changes should extract the remaining publisher-neutral response handling and stage transitions behind explicit interfaces, with regression tests before removing compatibility helpers. Avoid adding new publisher host checks to `browser_route.py`.

## Product installation

The `aletheia-nexus` console script has four entry paths: help, version, `doctor`, and `acquire`. `acquire` accepts one DOI directly or a TXT/CSV/JSON list. `--public-only` offers a no-browser first run for one DOI; the full path retains batch checkpoint, report, official API, and optional human-in-the-loop browser behavior. The old `scripts/batch_v06_download.py` remains a compatibility wrapper.

The source tree is installable (`python -m pip install -e .`). On 2026-09-24, the project owner registered a pending PyPI Trusted Publisher for `aletheia-nexus`; this does **not** reserve the name or make `pip install aletheia-nexus` work until the first upload succeeds. The distributions must still be built and inspected on the final commit.

## PyPI setup and release sequence

1. The project owner registered a pending Trusted Publisher for GitHub owner `shenxuekairui`, repository `aletheia-nexus`, workflow `.github/workflows/publish-pypi.yml`, environment `pypi`. Do not ask maintainers for passwords or a long-lived API token. Follow [PyPI's official setup guidance](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/) if the configuration ever changes.
2. The GitHub `pypi` environment has a required owner review and accepts only `v*` tags. The owner must approve the publish job when GitHub prompts. The publishing job has only `id-token: write`; the separate build job has `contents: read` and produces a checked distribution artifact.
3. On the final release commit, run format/lint, deterministic suite on Python 3.11 and 3.14, browser integration, Windows CI, package build, wheel install smoke, and appropriate authorized live DOI checks. Record the exact commit and all four CI conclusions as `success` (not `skipped`). Do not reuse the v0.6.0 test count as v0.6.1 evidence.
4. Merge the reviewed PR into `main`. Create an immutable `v0.6.1` tag at the merged commit and publish a GitHub Release only when the Trusted Publisher and environment are ready. The release workflow verifies that the tag equals the package version, runs tests and build checks, and uploads to PyPI through short-lived OIDC credentials.
5. In a fresh environment, verify `pip install aletheia-nexus`, `aletheia-nexus --version`, `aletheia-nexus doctor`, and a public-only DOI attempt. Only then advertise the PyPI install command without a caveat. If PyPI publishing fails, do not call the release complete; repair the publisher configuration or document the partial state before retrying the same version.

PyPI does not allow silently replacing an uploaded distribution with different bytes. Never publish a development version as `0.6.1` merely to test the pipeline; use the build/install smoke or TestPyPI as appropriate.

## CI and external acceptance

The existing draft/ready/main tier strategy remains. v0.6.1 adds one `windows-latest` job after the Linux fast gate; it tests the installed CLI, deterministic suite, and local real-Chromium integration without any publisher account. Standard hosted runners for a public repository do not consume private-repository minutes, but setup time and artifact storage are still worth minimizing. No live institutional browser profile or secrets enter CI.

The formal cross-institution positive-control entitlement acceptance deferred from v0.6.0 remains a separate task. A v0.6.1 code/packaging release must continue to disclose that actual publisher access depends on the user's legal subscription and network state. External first-time users should be invited through `CONTRIBUTING.md` and issue templates, with feedback about installation and status clarity—but their reports are not fabricated before they exist.

The owner chose to publish v0.6.1 before independent first-time-user feedback arrives, provided the release explicitly discloses that limitation. The three-minute onboarding goal remains unverified; [trial issue #3](https://github.com/shenxuekairui/aletheia-nexus/issues/3) stays open after publication. Neither that deferral nor the institution-acceptance deferral waives deterministic, browser, Windows, build, or PyPI upload checks.
