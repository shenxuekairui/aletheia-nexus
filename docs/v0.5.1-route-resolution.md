# v0.5.1 Route Resolution

> Aletheia Nexus v0.5.1 turns scholarly landing routes into explainable file candidates.

**Version:** 0.5.1  
**Layer:** Route Resolution（访问路径解析）  
**Status:** FINAL RELEASE CANDIDATE

## 1. Goal

v0.4 Discovery answers:

> Where might full text exist?

v0.5.0 Direct PDF Acquisition answers:

> If I already have a PDF candidate, can I retrieve it safely and verify that it is the target article?

v0.5.1 fills the gap between them:

```text
FullTextCandidate
(landing / resolver / repository / unknown route)
↓
safe page retrieval
↓
page semantics + identity evidence
↓
generic scholarly HTML signals
↓
DerivedFullTextCandidate[]
↓
v0.5.0 Direct PDF Acquisition + Validation
```

The layer does **not** claim that a derived URL is a valid PDF. It only makes the
route more concrete while preserving why and where the route was derived.

The central invariant is:

> **Derived Candidate ≠ Verified File.**

## 2. Architectural boundary

The v0.5 acquisition line is deliberately split into distinct responsibilities:

```text
v0.5.0  Direct PDF Acquisition + Validation
        one concrete PDF candidate → trustworthy file result

v0.5.1  Route Resolution
        one route/page → zero or more explainable PDF candidates

v0.5.2  Multi-route Acquisition
        coordinate many provider + derived routes until VERIFIED

later   Authenticated / Browser Acquisition
        SSO / CARSI / browser state / Human-in-the-loop
```

This separation is intentional. v0.5.1 does not become a hidden multi-route
downloader, and v0.5.0 does not accumulate publisher-page parsing logic.

## 3. Public API

```python
from aletheia_nexus.acquire.fulltext import resolve_full_text_route

result = resolve_full_text_route(
    candidate,
    expected_title="Optional known title",
)

print(result.status)
for derived in result.candidates:
    print(derived.candidate.url)
    print(derived.method)
    print(derived.role_hint)
    print(derived.evidence)
```

The result is a `RouteResolutionResult` containing:

```text
source_candidate
status
candidates
page
page_type
identity
error
attempts
elapsed_seconds
```

Each derived candidate keeps:

```text
candidate           normalized PDF-shaped FullTextCandidate
parent_url          route that led to derivation
source_page_url     actual page used for extraction
derivation method   why the URL was produced
role_hint           ARTICLE / SUPPLEMENT / UNKNOWN
evidence            human-readable derivation evidence
priority            deterministic acquisition-oriented priority
```

Provider provenance and AN derivation provenance remain separate. A URL derived by AN
from an OpenAlex landing page is not falsely represented as though OpenAlex directly
reported that PDF URL.

## 4. Resolution statuses

```text
RESOLVED
NO_FILE_CANDIDATES
PAGE_MISMATCH
AUTH_REQUIRED
ACCESS_BLOCKED
NOT_FOUND
TOO_LARGE
UNSAFE_URL
REDIRECT_ERROR
REQUEST_ERROR
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
INVALID_CONTENT
ERROR
```

Important semantics:

```text
401 → AUTH_REQUIRED
403 → ACCESS_BLOCKED
```

HTTP 403 alone is insufficient evidence that login or institutional authorization is
the cause. It can also represent WAF（Web 应用防火墙）, anti-bot, IP policy, or other
server-side blocking.

`NO_FILE_CANDIDATES` is not treated as an exception. It means the route was handled but
current generic evidence did not expose a concrete file route.

## 5. Safe page retrieval

Route pages reuse the v0.5 acquisition safety boundary:

- HTTP(S) only;
- hostname required;
- embedded credentials rejected;
- non-global/private/loopback/link-local literal IPs rejected;
- best-effort DNS preflight safety checks;
- redirects followed manually and every target revalidated;
- bounded redirect count;
- bounded timeout;
- bounded HTML/text body size;
- network/rate-limit/service errors keep explicit retry semantics.

Defaults:

```text
page timeout       30 s
page size          10 MiB
redirect limit      8
```

### Binary/PDF sniffing

A route advertised as a landing page can actually return PDF bytes directly. v0.5.1
therefore examines a small response prefix for the `%PDF-` marker.

A large response with an uncertain binary Content-Type such as
`application/octet-stream` is not rejected from `Content-Length` alone before this
sniffing step. Definite large HTML/text responses can still be rejected early.

If a PDF response is detected, v0.5.1 does **not** download the whole file. It returns a
`DIRECT_PDF_RESPONSE` derived candidate so v0.5.0 remains the only layer responsible
for file acquisition and validation.

## 6. Generic HTML evidence

v0.5.1 deliberately prefers standards and page semantics over a publisher-domain map.

Supported generic signals include:

### Scholarly metadata

```text
citation_pdf_url
bepress_citation_pdf_url
eprints.document_url
pdf_url
```

### HTML links

```text
<link type="application/pdf">
<link rel="alternate" ...>
<a>Download PDF</a>
<a>View PDF</a>
<a>Article PDF</a>
<a>Full text PDF</a>
```

### Embedded files

```text
<iframe>
<embed>
<object>
```

when type or URL evidence indicates PDF.

### JSON-LD（JSON 链接数据）

PDF media paths can be collected from structured media fields such as:

```text
contentUrl
downloadUrl
url
fileFormat / encodingFormat / contentType
```

### URL normalization

- relative links resolve against the final page URL;
- `<base href>` is honored when valid;
- fragments are removed;
- unsafe/non-HTTP schemes are ignored;
- duplicate routes merge evidence rather than creating duplicate candidates.

## 7. Page identity

Page identity is intentionally conservative:

```text
MATCH
MISMATCH
UNKNOWN
```

Strong evidence includes:

- target DOI in scholarly page metadata;
- very strong expected-title match when DOI metadata is absent.

A **different generic page title is not enough to emit MISMATCH**. Resolver bridges,
repository shells, access interstitials and challenge pages often use titles unrelated
to the paper.

`MISMATCH` requires explicit scholarly DOI metadata pointing to another work.

This policy was hardened after the real CDI corpus showed Elsevier LinkingHub and
challenge pages being incorrectly interpreted as wrong-paper pages when title conflict
alone was used.

## 8. Page semantics and precedence

The page classifier distinguishes:

```text
ARTICLE
LOGIN
ACCESS_DENIED
CHALLENGE
GENERIC
PDF_RESPONSE
UNKNOWN
```

Strong challenge/access-denied evidence describes the response actually served and has
priority over stale/copied scholarly metadata.

At the same time, generic account controls such as “sign in for saved searches” do not
turn an otherwise positively identified article page into `LOGIN`.

Resolution precedence is:

```text
CHALLENGE / ACCESS_DENIED → ACCESS_BLOCKED
LOGIN                     → AUTH_REQUIRED
explicit DOI mismatch     → PAGE_MISMATCH
otherwise                 → derive file candidates
```

This avoids both false authentication claims and false paper mismatches.

## 9. Document-role hints

Route Resolution uses:

```text
ARTICLE
SUPPLEMENT
UNKNOWN
```

as **hints**, not final document classifications.

Strong article metadata such as `citation_pdf_url` is an ARTICLE hint. Supporting
Information text/filenames become SUPPLEMENT hints.

Known auxiliary scientific PDFs such as:

```text
Reporting Summary
Peer Review file
Transparent Peer Review
Source Data
Decision Letter
Reviewer Comments
Author Checklist
```

remain `UNKNOWN` rather than being promoted to ARTICLE merely because the link also
contains “download PDF”.

Final authority remains v0.5.0 file validation. A role hint can improve ordering but
cannot create `VERIFIED` by itself.

## 10. HTTP → HTTPS route derivation

The CDI corpus exposed a real repository case where a provider-reported HTTP PDF route
failed while the corresponding HTTPS route was usable.

v0.5.1 therefore supports an explicit, traceable HTTPS alternative:

```text
http://host/path/file.pdf
↓
https://host/path/file.pdf
```

This is **derivation**, not normalization. The original route is preserved, and the new
candidate records:

```text
method = HTTPS_UPGRADE
parent_url = original HTTP route
```

AN does not globally rewrite arbitrary HTTP URLs and pretend that HTTP/HTTPS are always
equivalent.

## 11. Candidate ranking

Ranking answers:

> Which derived file route is most promising to hand to Acquisition next?

It is deterministic and evidence-based. Broadly:

```text
DIRECT_PDF_RESPONSE
>
citation_pdf_url
>
other PDF metadata
>
<link> PDF
>
JSON-LD PDF
>
semantic Download/View PDF anchor
>
embedded PDF
>
PDF-looking URL
>
HTTPS alternative
```

ARTICLE hints receive a modest bonus. SUPPLEMENT hints are strongly demoted. HTTPS
receives a small preference.

This is acquisition priority, not scholarly authority.

## 12. Fixed CDI real-network benchmark

v0.5.1 keeps the fixed corpus at:

```text
benchmarks/cdi_acquisition_10.json
```

Manual runner:

```text
scripts/manual_cdi_10_route_acceptance.py
```

The same ten papers span Springer Nature, ACS, Elsevier, Wiley, RSC, repositories,
open-access and access-restricted behavior. The corpus is intentionally reused instead
of replacing difficult cases with easier papers.

### Hardened real-network acceptance

A temporary GitHub Actions workflow ran the actual branch against the fixed corpus on
2026-09-16. It used OpenAlex Discovery only; no personal Unpaywall email was embedded in
CI. The workflow is removed from the final branch after acceptance so third-party
website changes cannot make ordinary CI flaky.

Final observed paper-level outcomes:

```text
VERIFIED                                      5 / 10
NO_FILE_CANDIDATE                             3 / 10
ACCESS_BLOCKED                                1 / 10
INVALID_PDF | RETRIEVED_UNVERIFIED | SUPPLEMENT  1 / 10
```

Verified routes included:

- Nature Communications: landing page → `citation_pdf_url` → verified Nature PDF;
- npj Clean Water: existing direct Nature PDF remained verified;
- older Springer OA: obsolete provider PDF failed, but DOI landing page exposed a new
  Springer PDF route that verified;
- Elsevier OA: HAL landing page exposed a repository document that verified;
- Wiley OA: PolyU repository landing page exposed a usable HTTPS file route despite the
  provider HTTP PDF route failing.

The hardened second run kept the same 5/10 verified result while improving semantics:

- PMC challenge pages became `ACCESS_BLOCKED / CHALLENGE`, not `PAGE_MISMATCH`;
- Elsevier LinkingHub generic bridges became conservative `NO_FILE_CANDIDATES`, not a
  false wrong-paper conclusion;
- Nature Reporting Summary / Peer Review files became `UNKNOWN` role hints instead of
  ARTICLE hints;
- Supporting Information remained rejected;
- **no wrong file was promoted to VERIFIED**.

### Remaining boundaries from the same corpus

- ACS pages returned server-side access blocking to the GitHub runner;
- RSC OA returned 403 and is correctly represented as `ACCESS_BLOCKED`, not automatically
  `AUTH_REQUIRED`;
- one HAL page matched the requested paper but exposed no file route in the retrieved
  HTML;
- Nature Water exposed an article PDF route, but the automated request did not yield a
  valid verified article; auxiliary PDFs were not falsely accepted.

These are intentionally **not** solved by guessed URL construction, publisher-specific
hardcoding, anti-bot bypass, or authentication circumvention.

## 14. Accepted non-goals

v0.5.1 intentionally does not implement:

- automatic multi-candidate orchestration;
- browser JavaScript execution;
- CARSI / SSO / institutional login;
- cookie/session persistence;
- CAPTCHA or anti-bot circumvention;
- paywall bypass;
- a publisher-specific adapter catalogue;
- guessed publisher PDF URL synthesis;
- OCR or scientific-content parsing;
- a literature database.

These exclusions are architectural boundaries, not hidden failures.

## 15. Why no further generic mechanisms were added after acceptance

The hardened real corpus did not expose evidence that another generic parser primitive
would materially improve v0.5.1 without crossing layer boundaries.

The remaining failures were access-blocking/authentication boundaries or pages that did
not expose a file in the retrieved HTML. Adding speculative meta-refresh rules,
publisher URL templates, browser automation, or guessed repository paths solely to
improve the benchmark score would violate the project's principles:

> solve real problems, preserve provenance, prefer explicit failure, and do not pay
> complexity cost before the requirement is demonstrated.

## 16. Next layer

v0.5.2 should build **Multi-route Acquisition（多路径获取编排）** on these two stable
primitives:

```text
Discovery Candidate
        ↓
Route Resolution when needed
        ↓
Direct PDF Acquisition + Validation
        ↓
try next route only when policy permits
        ↓
first VERIFIED article stops
```

That layer will own route-attempt policy and fallback history. v0.5.1 remains a stable,
independently testable route-to-candidate capability.
