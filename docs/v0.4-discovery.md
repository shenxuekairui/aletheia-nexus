# v0.4 Full-text Discovery — Final Contract

> Aletheia Nexus v0.4.2 final Discovery（全文发现）contract and freeze note.

## 1. Status

```text
Version: 0.4.2
Layer:   Full-text Discovery
Status:  FINALIZED / FROZEN FOR MERGE
```

v0.4 establishes a reliable boundary between scientific-object metadata and actual file acquisition.

Its responsibility is:

```text
Normalized DOI / Paper identity
↓
Discover possible access routes
↓
Normalize and merge candidate routes
↓
Expose provider status, provenance, timing and acquisition priority
```

Its responsibility is **not**:

```text
Download a file
Verify that a URL is a real PDF
Verify that a retrieved PDF is the target article
Resolve institutional authentication
```

Those belong to v0.5 Acquisition + Validation（获取与验证）.

## 3. Candidate semantics

### `CandidateUrlType`

```text
PDF
LANDING_PAGE
UNKNOWN
```

`PDF` means **provider-reported PDF candidate**. It is not file verification.

### `AccessType`

```text
OPEN_ACCESS
UNKNOWN
```

`UNKNOWN` must not be interpreted as closed access.

### `FullTextVersion`

```text
PUBLISHED
ACCEPTED
SUBMITTED
UNKNOWN
```

Version is provider-reported scholarly-version metadata, not an AN-verified file fact.

### `HostType`

```text
PUBLISHER
REPOSITORY
INDEX
RESOLVER
UNKNOWN
```

Real benchmark evidence justifies explicit route refinement for DOI/Handle resolvers, PubMed/DOAJ indexes and PMC repositories. v0.4 intentionally avoids a large hard-coded publisher-domain catalogue.

### `is_best`

`is_best` preserves a positive provider-side best-location signal. It is not a claim that AN has established a globally authoritative or best scholarly version.

## 4. URL identity and safety

Before a Candidate becomes an Acquisition input, v0.4 URL handling enforces:

```text
HTTP(S) only
hostname required
embedded credentials rejected
whole-value wrappers safely removed
fragment removed
scheme/netloc normalized
```

Persistent resolver identity rules proven by real corpus data:

```text
http://doi.org/...      → https://doi.org/...
https://dx.doi.org/...  → https://doi.org/...
https://www.doi.org/... → https://doi.org/...
http://hdl.handle.net/... → https://hdl.handle.net/...
```

Ordinary website HTTP/HTTPS schemes are not globally rewritten.

v0.4 only returns URLs. Network-safety policy for actually fetching arbitrary Candidate URLs belongs to v0.5 and must be considered before Acquisition is allowed to follow external routes automatically.

## 5. Candidate merge and priority

Canonical URLs are deduplicated.

Merged Candidate provenance preserves all providers that reported the route.

Free-text metadata follows a conservative rule:

```text
all non-empty reports agree
→ retain value

providers conflict
→ None / unknown
```

This applies to `license` and `source_name` so v0.4 does not silently select a conflicting provider statement.

Candidate ordering is **Acquisition Priority（获取优先级）**, not scholarly authority.

Current preference is driven by:

```text
open access
→ provider-reported direct PDF
→ scholarly version
→ route type
→ provider best-location signal
```

The ordering is deterministic.

## 6. Provider model

Default providers:

```text
OpenAlex
Unpaywall
```

Unpaywall requires an email. If it is not configured, the provider result is explicitly `SKIPPED` with zero attempts rather than being reported as a network or discovery failure.

OpenAlex API key is optional.

v0.4 does not add a third default Provider because the current real corpus does not show sufficient marginal route gain to justify another default external dependency.

Current future candidates:

```text
Semantic Scholar → benchmark-first broad fallback candidate
Crossref link    → possible acquisition hint through existing Metadata layer
CORE             → repository-focused fallback candidate
Europe PMC       → future biomed/life-science domain provider
```

A new Provider should be added only after a targeted gap corpus demonstrates unique usable routes, direct-file gain, domain-specific gain or acquisition-critical metadata that outweighs request, authentication, rate-limit, conflict and maintenance costs.

---

## 7. Failure model

Stable Provider outcomes:

```text
SUCCESS
NO_CANDIDATES
NOT_FOUND
SKIPPED
CONFIGURATION_ERROR
REQUEST_ERROR
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
PARSE_ERROR
ERROR
```

Only temporary failures are retried:

```text
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
```

The following are not retried automatically:

```text
NOT_FOUND
REQUEST_ERROR
PARSE_ERROR
CONFIGURATION_ERROR
```

Unexpected programming exceptions intentionally propagate instead of being converted into ordinary Provider failure.

## 8. Batch semantics

Batch status:

```text
SUCCESS
PARTIAL_SUCCESS
NO_CANDIDATES
NOT_FOUND
INVALID_DOI
ERROR
```

Important contract:

```text
SUCCESS
≠ verified full text retrieved

SUCCESS
= the Discovery workflow completed with one or more candidate routes and no real provider failure
```

A valid Candidate plus a real Provider failure becomes `PARTIAL_SUCCESS`.

Batch processing preserves original input, normalized DOI, error summary and elapsed time.

Normalized DOI deduplication is stable and optional.

## 9. Concurrency and timing

v0.4.1 measured that Discovery latency was almost entirely external Provider wait time.

v0.4.2 therefore introduces only one proven concurrency layer:

```text
one DOI
├─ OpenAlex
└─ Unpaywall
   run concurrently
```

Maximum provider workers are fixed at `2`.

Batch DOI items remain sequential.

Provider result order stays deterministic regardless of thread completion order.

Timing records include retry/backoff time.

After concurrency, benchmark metrics distinguish:

```text
provider work sum
provider critical path
provider overlap factor
discovery wall time
coordination estimate
batch wrapper overhead
```

They must not be interpreted as if concurrent Provider durations were additive wall time.

Connection pooling remains intentionally outside the final v0.4 change set. HTTPX Client pooling is a valid future transport optimization, but v0.4 freeze does not introduce a new client-lifecycle/injection abstraction without a dedicated measured acceptance case.

## 10. Provider contribution diagnostics

`summarize_provider_contributions()` evaluates:

```text
candidate_routes
unique_routes
shared_routes
exclusive_access_type
exclusive_version
exclusive_host_type
exclusive_license
exclusive_source_name
exclusive_is_best
metadata_disagreements
```

On shared routes, metadata counts as exclusive only when exactly one Provider supplies an informative value.

Different informative values become disagreement counts; evaluation does not silently appoint one Provider as authoritative.

## 11. Real-network acceptance

Final v0.4 performance evidence uses the repository corpus:

```text
benchmarks/discovery_water_electrolysis_30.txt
```

The corpus covers multiple publisher and hosting ecosystems, including mainstream and less-mainstream platforms.

Measured baseline:

```text
v0.4.1 sequential
30 / 30 SUCCESS
batch elapsed 66.484 s
```

Measured v0.4.2:

```text
30 / 30 SUCCESS
97 merged candidates
56 OA candidates
16 provider-reported PDF candidates

batch elapsed          32.783 s
measured speedup        2.03x
elapsed reduction      50.7%
provider overlap        1.80x
coordination estimate   0.029 s
```

Work-level coverage remained unchanged:

```text
works with candidates       30
works with OA candidate     20
works with PDF candidate    15
works with non-resolver     24
works with pub/repository   17
```

The candidate count decreased from 98 to 97 because equivalent HTTP/HTTPS Handle routes became one canonical route. This is intended deduplication, not coverage loss.

Provider contribution on this chemistry/energy corpus:

```text
OpenAlex
  routes 97
  unique 41
  shared 56

Unpaywall
  routes 56
  unique 0
  shared 56
```

These figures are engineering evidence for this corpus, not a claim of universal cross-domain coverage.

## 12. Test and release quality gate

Final v0.4 CI targets minimum and current-upper tested Python boundaries:

```text
Python 3.11
Python 3.14
```

Every CI environment runs:

```text
editable installation
pip check
Ruff format check
Ruff static check
compileall src
pytest
```

Real third-party API calls are intentionally excluded from CI and kept in manual acceptance scripts so external-service instability cannot create false code regressions.

Test files live under `tests/`; production packages under `src/` must not contain pytest modules.

## 13. Intentional non-goals of v0.4

The following must not be pulled back into Discovery during maintenance:

```text
PDF download
redirect/file retrieval policy
landing-page HTML parsing
Content-Type validation
PDF magic-byte validation
page-count / parseability validation
article identity validation
supporting-information discrimination
file storage / hashing / atomic rename
institutional authentication
CARSI / SSO
browser automation
captcha bypass
batch-level concurrency without rate-limit evidence
```

These belong to v0.5 or later.

## 14. Transition to v0.5

The next stable chain is:

```text
DiscoveryResult
↓
Acquisition Strategy
↓
HTTP / landing-page retrieval
↓
Retrieved File
↓
PDF Validation
↓
Paper Identity Validation
↓
Verified File
```

Recommended implementation order:

```text
v0.5.0 Direct Acquisition
↓
v0.5.1 PDF Validation
↓
v0.5.2 Landing Page Resolution
↓
v0.5.x Authenticated Acquisition + Human-in-the-loop
```

This boundary is the most important architectural outcome of v0.4: **a route is evidence about where content may exist; only Acquisition + Validation can turn that evidence into a trusted scientific file.**
