## 已收敛的逻辑

| 原实现的问题 | 最终处理 |
| --- | --- |
| PDF 接口在两个位置各自执行导航、等待、HTTP 重试，之后又可能进入 native 恢复 | 合并为一条接口恢复路径：HTTP 检出交互挑战后导航一次，在正常浏览器等待与交付流程内恢复；去掉冗余 `_allow_endpoint_handoff` 开关。 |
| Wiley 的“控件优先”实际上排除了无交付时的常规候选请求 | 偏好只影响顺序。控件不存在或点击未交付时，仍可请求页面已给出的 PDF 地址；不把一次站点特性推广成永久禁用 HTTP。 |
| 主页面、点击后及每个弹窗分别请求 PDF，重复地址和总量失控 | 主流程统一备用 HTTP 候选请求，按去除 fragment 的 URL 去重，共用现有 `max_pdf_candidates`。弹窗只观察访问状态、地址并触发浏览器交付，保持存活直到响应消费完毕。native-only 路径也不通过弹窗重放 context HTTP。 |
| 推导出的规范 PDF 地址排在页面明确提供的地址之前，可能先触发挑战 | 元数据、页面与网络已经观察到的地址优先，规范地址作为后备。新 Chromium 夹具先复现失败，调整后同样输入获得已验证正文；该证据不等于证明历史官网失败原因。 |
| 三十余个终态重复组装，容易漏掉已有挑战或文件尝试 | 使用一个局部结果构造入口保留当前路径的观察；递归恢复仍显式合并历史。没有新增公开状态类型或重试框架。 |
| Wiley 窄适配器仍读取隐藏/消失控件，TF 单个属性读取没有显式超时 | Wiley 先筛可见控件、单次读取 500 ms、扫描 10 秒上限，发现歧义立即停止；TF 属性读取显式有界。与共享控件的已知阻塞模式一致。 |

备用 HTTP 预算是一次 route pass 的预算。认证成功后恢复的新 pass 可以重新尝试；浏览器自身的受限 fetch/交付捕获有各自已有预算。这里没有声称实现了整个任务的统一耗时上限。默认人工等待仍可无限等待，`--non-interactive` 与显式有限等待的语义不变。

## 架构职责

沿用现有分层：出版社适配器提供官方入口、页面语义和尝试顺序；`browser_route` 负责路径调度、候选预算、挑战恢复及结果汇总；`browser_engine` 负责 Chromium/viewer 的字节交付；共享 fulltext 验证决定正文是否 VERIFIED；BrowserSession 与批次检查点负责会话和队列恢复。

本次只在上述边界内去重和修正执行顺序。生产源码净减少 **363 行**，其中 `browser_route.py` 净减少 **377 行**。保留原有浏览器依赖及配置接口，没有新增依赖或公开配置项。

为了严格控制范围，不实施新的通用状态机、插件框架、每家出版社的独立下载流水线、后台监视服务、机构黑名单或跨设备凭据迁移。pending-page 容器的形式、全文件拆分及更多兼容包装也没有足够收益，保持现有实现；不能仅因代码较长就再引入一层抽象。
