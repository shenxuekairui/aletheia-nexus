# v0.5.0 Direct PDF Acquisition

> Aletheia Nexus v0.5.0 first Acquisition（获取）slice.

**Version:** 0.5.0  
**Layer:** Direct PDF Acquisition + Validation  
**Status:** FINALIZED / FROZEN FOR MERGE

## 1. Goal

v0.5.0 converts one provider-reported direct PDF candidate into a locally stored,
traceable result only when file and paper identity checks support that conclusion.

```text
FullTextCandidate(url_type=PDF)
↓
safe retrieval
↓
PDF structure validation
↓
paper identity validation
↓
document-role check
↓
VERIFIED local PDF + acquisition sidecar
```

The key invariant is:

> Downloaded bytes are not trusted scientific content until validation succeeds.

In particular:

```text
Candidate ≠ downloaded file
Downloaded file ≠ valid PDF
Valid PDF ≠ target paper
Target paper ≠ main article
```

## 2. Scope

v0.5.0 intentionally supports only one direct PDF Candidate at a time.

It does:

- HTTP(S) retrieval with Acquisition-specific safety preflight;
- manual redirect handling with the same checks on every hop;
- streaming download with a default 100 MiB limit;
- SHA-256 calculation while downloading;
- explicit authorization, request, network, rate-limit, and service failure semantics;
- bounded retries only for transient failures;
- PDF header and parser validation;
- page-count and encryption reporting;
- limited first-pages text extraction;
- DOI exact-match identity evidence;
- conservative title fallback when an expected title is supplied;
- conservative Supporting Information detection;
- atomic promotion of persisted files;
- JSON sidecar provenance next to persisted files;
- optional retention of unverified material for Human-in-the-loop（人在回路中） review.

It does not:

- parse Landing Pages to discover PDF links;
- automatically try multiple Discovery candidates;
- perform CARSI / SSO / browser login;
- bypass paywalls, access controls, or CAPTCHA;
- parse article scientific content;
- create a literature database;
- run batch-level acquisition concurrency;
- claim adversarial DNS-rebinding-proof networking.

Those remain later slices or future hardening work.

## 3. Public API

```python
from aletheia_nexus.acquire.fulltext import acquire_direct_pdf

result = acquire_direct_pdf(
    candidate,
    output_dir="downloads",
    expected_title="Optional known paper title",
)
```

The input must be a v0.4 `FullTextCandidate` whose `url_type` is `PDF`.
A Landing Page candidate is rejected by design in v0.5.0.

The stable public surface also exports the result/status models and Acquisition
exception hierarchy from `aletheia_nexus.acquire.fulltext`.

## 4. Stable result statuses

```text
VERIFIED
RETRIEVED_UNVERIFIED
SUPPLEMENT
MISMATCH
INVALID_PDF
AUTH_REQUIRED
NOT_FOUND
TOO_LARGE
UNSAFE_URL
REDIRECT_ERROR
REQUEST_ERROR
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
ERROR
```

`VERIFIED` requires:

```text
valid PDF
+
identity MATCH
+
document role ARTICLE
```

`RETRIEVED_UNVERIFIED` means a structurally valid PDF was retrieved but current
evidence is insufficient to assert that it is the requested article.

HTTP 200, `Content-Type: application/pdf`, a `.pdf` suffix, or successful parsing
alone never implies `VERIFIED`.

## 5. Identity policy

Identity validation is deliberately conservative.

Primary evidence:

```text
target DOI found in inspected PDF text
```

Fallback evidence when `expected_title` is supplied:

```text
exact normalized title occurrence in inspected first-pages text
or
very strong similarity to the dedicated PDF metadata title
```

The title fallback intentionally does **not** use loose whole-page vocabulary overlap.
Scientific terms often recur in abstracts, references, or neighboring material and
would create false verification.

Outputs are:

```text
MATCH
MISMATCH
UNKNOWN
```

`UNKNOWN` is preferred over guessing. Missing DOI evidence alone is never treated as
a mismatch.

A locked encrypted PDF that cannot be opened remains `UNKNOWN` even if its metadata
title appears to match. Metadata alone is not sufficient to promote an unreadable
file to `VERIFIED`.

A mismatch is emitted only when strong conflicting evidence exists.

## 6. Supporting Information

A PDF associated with the target paper can still be Supporting Information（补充材料）.

v0.5.0 checks strong supplement indicators from:

- source filename;
- PDF metadata title;
- text near the beginning of the document.

The text check is intentionally limited to the document lead. A normal article that
later says “Supporting Information is available” must not be classified as the
supplement itself.

A detected supplement returns `SUPPLEMENT` and is not promoted as a verified article.

## 7. PDF inspection dependencies

v0.5.0 uses `pypdf` for structural inspection and limited text extraction.

The package installs:

```text
pypdf[crypto]
fontTools
```

`pypdf[crypto]` supplies the cryptographic backend required for AES-encrypted PDFs.
This matters because some PDFs are permission-encrypted but still open with an empty
user password; v0.5.0 explicitly attempts that case before declaring the file locked.

`fontTools` improves text extraction from PDFs that use CFF / Type1 font encodings.
It became a required dependency after real-network acceptance exposed repeated font
encoding warnings on a genuine scientific PDF. Re-running the same corpus with
`fontTools` removed those warnings without changing the expected classifications.

## 8. Retrieval safety

Each initial URL and redirect target must:

- be HTTP(S);
- have a hostname;
- contain no embedded credentials;
- not be an obvious localhost / private / link-local / reserved / otherwise
  non-global literal IP;
- pass a best-effort DNS preflight that rejects resolved non-global addresses.

Redirects are handled manually rather than delegated to unrestricted automatic
following, so every next hop is normalized and checked before retrieval.

### Security boundary

The DNS check is a **preflight defense**, not connection pinning. HTTPX performs the
actual network resolution again when connecting, so v0.5.0 does not claim complete
protection against an adversarial DNS rebinding / time-of-check-to-time-of-use attack.

That stronger network isolation would require a different transport architecture
(e.g. resolved-address pinning or a restricted network sandbox). For the current
local-first direct-acquisition slice, the preflight check is an intentional bounded
safety improvement rather than a claim of perfect SSRF isolation.

## 9. Retrieval and retry contract

Defaults:

```text
max_bytes       100 MiB
max_redirects   8
timeout          30 s
max_attempts     3
backoff_base      1 s
```

Only these transient classes are retried automatically:

```text
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
```

These are not retried:

```text
AUTH_REQUIRED
NOT_FOUND
TOO_LARGE
UNSAFE_URL
REDIRECT_ERROR
REQUEST_ERROR
```

Unknown programming errors and local filesystem errors propagate instead of being
silently disguised as network failures.

## 10. Storage and provenance

Verified files use deterministic local names derived from DOI and content hash:

```text
<safe-doi>-<sha256-prefix>.pdf
<safe-doi>-<sha256-prefix>.acquisition.json
```

The sidecar records:

- target DOI and optional expected title;
- original Candidate semantics and provenance;
- requested and final URLs;
- redirect chain;
- HTTP status and Content-Type;
- byte count and SHA-256;
- PDF validation result;
- identity and document-role evidence;
- attempts and elapsed time;
- acquisition timestamp.

Unverified material is deleted by default. With `keep_unverified=True`, it is stored
under `_unverified/` with the same sidecar mechanism for manual inspection.

File lifecycle rules are deliberately conservative:

- temporary `.part` files are removed on failed retrieval/validation;
- a deleted temporary file is not exposed as a valid `local_path`;
- a newly promoted PDF is rolled back if its sidecar cannot be written;
- an already-existing correct PDF is never deleted merely because a later sidecar
  refresh fails;
- sidecar writes use a temporary file and atomic replacement.

## 12. Real-network acceptance

A temporary GitHub Actions workflow was used only for release acceptance. It ran the
actual v0.5.0 implementation against representative public network endpoints on
2026-09-15. The workflow is intentionally removed from the final branch so changing
third-party websites do not make normal CI flaky.

Observed cases:

| Case | Observed result | Key evidence |
| --- | --- | --- |
| Frontiers article `10.3389/fchem.2022.913419` | `VERIFIED` | 1,078,627-byte PDF, 9 pages, target DOI + expected title found |
| CaltechAUTHORS SI for `10.1021/ja510442p` | `SUPPLEMENT` | 2,070,044-byte PDF, 44 pages, 1 redirect to S3, supplement marker at document start |
| `example.com` passed as a fake PDF candidate | `INVALID_PDF` | 559-byte HTML response, no PDF header |
| MDPI article route `10.3390/catal14050307` | `INVALID_PDF` in the runner environment | `/pdf` returned a 2,226-byte non-PDF response; v0.5.0 correctly refused to persist it |
| Taylor & Francis `...?needAccess=true` route | `AUTH_REQUIRED` | server returned an authorization boundary rather than a usable PDF |

The MDPI observation is not evidence that the article has no PDF. It demonstrates a
real acquisition boundary: a public-looking PDF route can return anti-bot,
interstitial, or otherwise non-PDF content to an automated client. v0.5.0's job is to
refuse false success; solving such publisher-specific access paths belongs to later
Landing Page / authenticated acquisition work.

The real-network suite was run again after adding `fontTools` and `pypdf[crypto]`.
The expected classifications were unchanged, and the CFF font warnings seen in the
first run disappeared.

## 13. Known boundaries accepted for v0.5.0

The following are deliberate non-blockers rather than hidden defects:

- DNS safety is preflight-only, not adversarial connection pinning;
- a challenge/interstitial HTML response is currently represented as `INVALID_PDF`
  rather than a publisher-specific blocked/challenge status;
- reacquiring the same content refreshes the sidecar rather than maintaining a full
  append-only acquisition history;
- failed retrievals do not persist partial redirect traces to disk;
- identity validation inspects only limited first-page text and does not perform OCR;
- title verification is intentionally conservative and can yield `UNKNOWN` for valid
  papers whose text cannot be reliably extracted.

These boundaries should only be changed when real downstream requirements justify the
additional complexity.
