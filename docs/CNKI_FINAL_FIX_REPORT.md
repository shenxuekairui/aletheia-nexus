## 已落地的修复

### 准确检索

- 支持 DOI 解析题名和直接题名输入；完整身份题名与受长度限制的检索词分开。
- 中文使用可见菜单选择篇名；化学式运算符加引号，英文兼容中文译名候选，但译名不是最终身份通过的证据。
- 首轮候选全部失败时，仍允许一次中文长短语回退；跨查询对同一候选去重。
- 溯源记录实际检索字段，而非假定已经选择的字段。

### 稳定获取与避免重复下载

- 实地读取 #1 的 PDF 控件，确认其 `href` 为 `bar.cnki.net/bar/download/order`，`onclick` 为 `WriteKrsDownLog()`。
- 对这个已观察到的控件地址，优先由同一 BrowserContext 请求原 URL，保留机构 Cookie、URL 安全检查、重定向、CAJ 拒绝和文件大小限制。成功路线单独标为 `cnki_pdf_control_request`，不再执行第二次原生下载。
- 返回登录/验证码时交给用户；权限限制、超限或 CAJ 不通过原生重新点击绕过。仅对没有认证信号且未返回 PDF 的 JavaScript 壳页回退原生路径。
- 其他控件继续支持原生附件、弹窗附件和 PDF 响应；响应头到达不等于文件完成，收到请求完成事件后才读取正文。临时读取失败可再次读取，失败传输不读取不完整正文。
- `download_started` 在 PDF 请求/点击阶段设置。保存未成功不再等同于从未下载；会话重连、通用来源回退及批次内部重试不会重新执行已开始但会话关闭的 CNKI 下载。

### 人工认证续跑

- 默认直接 Python API 和单篇 CLI 等待用户，没有固定认证超时；显式配置的超时、非交互及取消行为仍有效。
- 识别实际登录表单、可见 iframe、验证码及“自动登录”页面；普通导航上的登录入口不触发认证。
- 提示消失后需连续两次观察到已渲染内容；认证弹窗自行关闭时只在存活、无认证提示且就绪的父页面继续。
- 保存阶段新出现的认证弹窗也纳入检测，保留弹窗及其父页面，避免清理父页面间接关闭认证现场。
- 人工完成后先等待自动恢复的下载；存在未完成 PDF 响应时不重复点击。确需恢复控件时最多再点击一次。
- 批次 API 与 CLI 默认在未解决的认证处停止；继续后续论文需显式选择。已验证文件继续受原 checkpoint/哈希机制保护。

### 身份与溯源

- PDF 专用 DOI 提取处理全角标点及排版空白；用户 DOI 校验保持严格。
- 化学式先做 Unicode 兼容规范化，再处理下标，兼容全角 `ＣＯ＿２` 与 PDF 的 `CO 2` 排版。
- 首页参考文献区域之前，唯一明确 `DOI:` 标记与目标冲突时，即使题名相同也不得晋升。
- 结构、正文角色、补充材料、加密及首页证据门槛保持；SHA-256 不替代论文身份核验。
- 文件路线、实际字段及 URL 重定向保留在现有 sidecar；不记录账号、密码或 Cookie，签名 URL 值脱敏。

## 使用与边界

```powershell
python scripts/download_cnki.py --doi "10.13822/j.cnki.hxsj.2024.0476" --profile cnki
python scripts/download_cnki.py --title "论文完整题名" --author "第一作者" --profile cnki
python scripts/batch_v06_download.py dois.txt --cnki --output-dir downloads/cnki
```

标题模式仍需从详情页或 PDF 首页确认真实唯一 DOI；不生成虚构标识。显式认证超时后，临时自有会话退出会关闭浏览器；需要超时返回后继续保留现场时使用调用者持有的 BrowserSession 或外部 CDP 会话。

下一步是用户完成当前机构认证，再核验 #1 新文件及溯源，随后依次验收 #3/#6。遇到新的安全认证仍停止。只有实际文件通过结构、身份、角色及哈希核对，才能报告 `VERIFIED`。

## 浏览器崩溃根因修复（2026-10-09）

### 根因与本机证据

根因定位为 Chromium 的持久下载历史管理回归 [556160935](https://issues.chromium.org/issues/556160935)，不是知网要求登录，也不是 AN 主动关闭浏览器。上游确认 DevTools 下载代理遗漏 `SupportsHistoryLoading()` 转发，历史与当前下载项合并时可能引用已释放对象；[Edge 团队确认在 155 修复](https://github.com/MicrosoftEdge/DevTools/issues/461)。本机两份 Edge 154 dump 的 `0xC0000005`、固定故障偏移，以及下面的跨版本对照共同支持归因。

本次使用微软官方 cdb 在独立诊断目录离线分析 dump，没有上传内存文件。公开 PDB 在本机未能解析成功，导出符号附近的函数名不能作为准确调用栈；不据此归咎于遥测、输入法或安全软件。

关键本地实验使用临时 profile、循环回环 HTTP 附件与重定向，文件字节逐次核对，不涉及 CNKI 订阅：

| 对照 | 结果 |
| --- | --- |
| Chromium `153.0.8010.12`，全新 profile | 4 次原生附件成功 |
| 同一 153 profile 关闭后重新启动 | 首次再次下载即崩溃，`Download.save_as` 观察到 TargetClosedError；新 dump 为 `0xC0000005` |
| Chrome for Testing `155.0.8059.39`，原 profile 连续两次启动 | 12 次原生附件成功，无崩溃 |
| 将刚刚在 153 崩溃的诊断 profile 复制给 155，保留 History/shared_proto_db；连续两次启动 | 12 次原生附件成功，无崩溃 |
| 正式 BrowserSession，复用同一配置启动三次，每次两份附件 | 6 次原生附件成功；认证测试 Cookie 保留 |

后面三项共 30 次原生附件成功，没有同会话 HTTP 请求兜底、历史清空或端口替换。新 profile 首次成功不是验收条件，带历史重启与保留故障状态的对照才是关键。本次消除的是已识别的这项回归，不能保证浏览器永无其他崩溃。
