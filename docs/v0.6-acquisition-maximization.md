# Aletheia Nexus v0.6 — Acquisition Maximization

> Canonical contract for the v0.6 access layer.

**Package line:** `0.6.x`

**Scope:** maximize legitimate scientific full-text acquisition across public,
direct, official-API, authenticated, institutional, browser-session and human-assisted access

**Status:** FIRST PUBLIC CODE RELEASE / FORMAL INSTITUTIONAL QUALIFICATION DEFERRED

The public code release requires the final-head CI evidence in §16. Formal
institutional access qualification remains deferred, not silently presumed.
A DOI's publisher terms are part of legitimate access.

The `v0.5.2` tag in the private development archive remains immutable; the
clean public repository does not carry that old tag or commit history. v0.6 adds an access layer that escalates
only when the v0.5 workflow does not produce a `VERIFIED` main article. The
shared `fulltext/identity.py` and `validation.py` validation layer did receive
targeted regression fixes for reproducible Nature/ACS false negatives and a
later-page DOI false positive; those changes do not alter the private historical tag.
An explicit user-selected local PDF is an exception: it can enter the shared
scientific validation gate directly, without any network acquisition.

---

## 1. Why v0.6 exists

The v0.5.2 fixed 20-paper stress corpus produced:

```text
CDI                       4 / 10 VERIFIED
Seawater desalination     2 / 10 VERIFIED
------------------------------------------
Combined                  6 / 20 = 30%
```

No false `VERIFIED` was observed. The dominant remaining gap was no longer
scientific identity validation: many correct publisher routes were discovered,
but ordinary unauthenticated HTTP retrieval encountered authentication,
institutional access, JavaScript challenges, CAPTCHA, WAF/bot interstitials, or
browser-only download behavior.

v0.6 therefore optimizes a different objective:

> **When the user has legitimate access, or a legitimate public copy exists,
> maximize the probability of obtaining the correct main-article PDF without
> weakening verification.**

The engineering target is not a literal promise of 100% acquisition. Third-party
availability, subscription entitlement, MFA, CAPTCHA policy, publisher UI changes
and network failures are outside AN's control. The design goal is to approach the
available-access ceiling while preserving correctness and provenance.

---

## 2. Governing invariants

v0.6 inherits all v0.5 invariants and adds:

```text
Authenticated response ≠ Valid PDF
Valid PDF ≠ Target Paper
Target Paper ≠ Main Article
Browser success ≠ VERIFIED
Login completed ≠ Entitlement exists
Challenge detected ≠ Permission to bypass it
Persistent session ≠ Permission to persist secrets in provenance
```

The most important rule remains:

> **Only scientific file validation can create `VERIFIED`.**

Authentication and browser automation may change how bytes are obtained. They do
not change what counts as the correct scientific artifact.

## 3. Architecture

```text
DOI
↓
user-selected local PDF? ─── yes ─→ shared scientific validation gate
↓ no
publisher requires user-operated access? ─── yes ─→ INTERACTION_REQUIRED
↓ no
v0.5 public/direct multi-route acquisition
↓
VERIFIED? ───────────── yes ─→ stop
↓ no
official authenticated provider API when configured/applicable
├─ current provider: Elsevier Article Retrieval API (PDF)
└─ same scientific validation gate
↓ still not VERIFIED
Browser recovery plan
↓
prioritize explicit AUTH_REQUIRED / ACCESS_BLOCKED routes
↓
publisher / resolver / repository / discovery routes
↓
dedicated persistent browser profile
↓
render JavaScript + reuse legitimate session state
↓
challenge detection
├─ browser-native challenge clears automatically
├─ SSO / login / MFA / CAPTCHA → bounded human handoff
├─ entitlement boundary → explicit terminal evidence
└─ access denied → explicit terminal evidence
↓
PDF acquisition paths
├─ captured browser PDF response bytes
├─ BrowserContext.request with shared cookie jar
├─ browser download event
└─ bounded semantic PDF control click
↓
existing PDF structural validation
↓
paper identity validation
↓
document-role validation
↓
VERIFIED main article
```

The browser layer is deliberately split into:

```text
browser.py
→ persistent profile + Playwright lifecycle + source-route budget

browser_route.py
→ one browser route: challenge handling, PDF capture and validation
```

This keeps browser-session complexity separate from per-route acquisition
complexity.

Documented publisher PDF URL derivation is centralized in
`access/publisher_routes.py`, shared by static recovery planning and live
browser navigation. It yields candidates, never access or identity proof.

## 4. Official authenticated provider API

v0.6 treats a publisher-supported authenticated API as a first-class access path
when it provides the main-article PDF and the user has legitimate credentials.

The first implemented provider is Elsevier's ScienceDirect Article Retrieval API:

```text
DOI
→ https://api.elsevier.com/content/article/doi/<doi>
→ Accept: application/pdf
→ X-ELS-APIKey
→ optional institution token / bearer token
→ optional documented amsRedirect=true Author Manuscript fallback
→ bounded, redirect-validated PDF retrieval
→ shared scientific artifact validation
```

Configuration secrets are represented by `ElsevierAccessConfig`; secret fields
are excluded from dataclass `repr`. The live acceptance runner can read:

```text
ELSEVIER_API_KEY
ELSEVIER_INST_TOKEN
ELSEVIER_BEARER_TOKEN
```

No secret value is written to sidecars or acceptance reports. Provenance records
only the provider and credential *mode* used. The maximized acquisition API
automatically discovers configured official-provider credentials from environment
variables by default; callers may disable this with `auto_official_api=False`.

By default, `ElsevierAccessConfig.allow_author_manuscript_fallback=True` enables
Elsevier's documented `amsRedirect=true` behavior. If the requester lacks
Version of Record entitlement but Elsevier exposes an Author Manuscript through
that API mechanism, AN may retrieve it; it still must pass the same DOI/title and
main-document validation before becoming `VERIFIED`. The fallback can be
explicitly disabled.

The API route is attempted only after v0.5 fails and only when DOI/metadata/route
evidence indicates Elsevier/ScienceDirect. If the API does not produce a verified
artifact, browser recovery still proceeds.

## 5. Persistent authenticated session

v0.6 uses a dedicated AN browser profile, defaulting to:

```text
~/.aletheia-nexus/browser-profiles/<profile_name>
```

A dedicated profile is preferred over attaching to the user's everyday browser
profile because it is easier to reason about, isolate, manage and delete, and
modern Chromium-family browsers increasingly restrict automation against the
default profile. Because it may contain active authenticated session state, it
should not be casually copied to cloud-sync or shared backup locations.

The profile may contain sensitive cookies/local storage created by legitimate
login flows. Therefore:

- it lives outside the repository by default;
- AN attempts restrictive directory permissions where the OS supports them;
- credentials, cookies, local-storage values and tokens are not copied into
  acquisition sidecars;
- browser-authenticated URL query values are redacted from persisted provenance.

A user normally logs in once in the visible AN browser. Later papers can reuse the
same legitimate session until it expires.

Browsers launched by AN use the process-scoped Chromium
`--no-proxy-server` argument and the dedicated profile above. This makes AN's
publisher traffic direct without changing the operating-system proxy or the
user's everyday Edge/Chrome profile. An explicitly attached external CDP browser
retains its existing network configuration; AN does not mutate proxy settings on
an already-running user-controlled browser.

AN deliberately keeps Service Worker（服务工作线程）behavior enabled in the
production browser context. Disabling Service Workers is useful for deterministic
network-mocking tests, but can change how a real publisher/login application
behaves. v0.6 prefers browser fidelity over test-only simplification; network
observability is handled through BrowserContext events and bounded request guards
instead of globally disabling site Service Workers.

For sequential batch acquisition, callers should keep one `BrowserSession` alive
across DOI-level calls. This preserves not only the on-disk cookie/profile state but
also short-lived in-memory SSO and challenge state. The fixed v0.6 live acceptance
runner uses this mode.

The public `acquire_full_text_batch_maximized()` workflow provides this behavior
without requiring callers to write their own session loop. It additionally provides:

- normalized DOI deduplication while preserving input order;
- one lazy, sequential browser session for the complete batch;
- atomic per-item checkpoint updates;
- resume only for existing `VERIFIED` files whose SHA-256 still matches;
- bounded retry of internal `ERROR` outcomes, never entitlement/access failures;
- interactive CLI handoff that prints the challenge and waits until it clears;
- item-level `INTERACTION_REQUIRED` when a bounded wait expires or is canceled,
  with later items continuing by default and opt-in whole-batch stopping;
- credential-free summary records and progress callbacks.

Non-success checkpoint records are diagnostic only. They are retried on the next run,
because the user may have refreshed an institutional session, completed a login, or
changed to a network where their existing entitlement is available. A checkpoint can
never promote an unverified artifact to `VERIFIED`.

The batch CLI exposes separate budgets for public route discovery and authenticated
browser work (`--base-timeout`, `--max-route-attempts`, `--max-file-attempts`,
`--navigation-timeout`, `--request-timeout`, `--max-source-routes`, and
`--max-pdf-candidates`). This prevents one publisher page with many stale candidates
from monopolizing the batch. In external-CDP navigation mode, an interaction page is
kept open and a later run resumes it only when its title strongly matches the current
paper. The JSON report includes credential-free browser/challenge diagnostics, but no
paper text, cookies, tokens, or signed URLs. The interactive CLI treats an omitted
`--interaction-timeout` as an unbounded human handoff: it polls the visible page until
the challenge clears or the user interrupts the whole command with `Ctrl+C`
(already-written per-item checkpoints remain available; a complete final batch
report is not guaranteed). Supplying a numeric timeout
keeps the older bounded behavior, while `--non-interactive` disables human waiting.
Library callers retain the bounded default unless they explicitly set
`wait_for_interaction=True`.

### 5.1 External real-browser handoff

Some anti-bot systems repeatedly challenge a browser that was launched directly
by an automation framework even when the user completes the visible CAPTCHA.
For that measured failure mode, v0.6 also supports attaching to an
already-running user-controlled Chromium-family browser through a **loopback-only
CDP (Chrome DevTools Protocol，Chrome 开发者工具协议) endpoint**.

This is a human-handoff mode, not fingerprint spoofing:

```text
user starts normal Chrome/Edge with a local debugging port
↓
user opens the target article and completes legitimate login/CAPTCHA normally
↓
AN attaches to 127.0.0.1
↓
AN reuses the already-open HTTP(S) tab without re-navigating it
↓
PDF discovery / authenticated retrieval / scientific validation
```

Example configuration:

```python
config = BrowserAccessConfig(
    cdp_endpoint="http://127.0.0.1:9222",
    interactive=True,
)
```

Only loopback HTTP(S) CDP endpoints are accepted. AN does not close the external
browser when the acquisition session ends. In attached mode the current matching
web tab is preferred and the original source URL is not automatically revisited,
which avoids destroying transient session/challenge state that the user has
already established.

## 6. Challenge handling

Stable challenge classes:

```text
NONE
BOT_CHALLENGE
CAPTCHA
AUTHENTICATION
SSO
MFA
ENTITLEMENT
ACCESS_DENIED
UNKNOWN
```

Policy:

1. Let the real browser execute normal JavaScript/cookie challenges first.
2. Re-check rendered **visible text**, not arbitrary script-bundle text.
3. If a legitimate SSO/login/MFA/CAPTCHA step still remains, expose a bounded
   Human-in-the-loop handoff.
4. After the user completes the challenge, automatically continue the same
   acquisition attempt with the now-authenticated session.
5. If the page explicitly says the account/institution has no entitlement, record
   that boundary rather than pretending another login will fix it.
6. Do not implement credential guessing, CAPTCHA-solving services, stealth
   fingerprint spoofing, paywall bypass or uncontrolled anti-bot circumvention.

The objective is high recovery with stable legitimate sessions, not an arms race
against access controls.

## 7. PDF recovery paths

v0.6 uses multiple browser-backed paths because publishers behave differently.

### 7.1 Captured browser response

If the real page request already returned `application/pdf`, AN captures those
exact response bytes and validates them immediately. This is important for
one-time signed URLs and requests whose headers cannot be reproduced later.

### 7.2 Context request

The Playwright browser context exposes an HTTP request client that shares the
context cookie jar. AN can request a concrete PDF URL with the authenticated
session and a source-page `Referer` when available.

### 7.3 Browser download event

If clicking/navigating triggers a browser download instead of an ordinary
response, AN captures the downloaded file and sends it to the same validation
pipeline. Browser-local sources such as `blob:` URLs are not discarded: AN
retains the parent HTTP(S) article route as auditable provenance and lets the
normal scientific validation gates decide whether the downloaded bytes are the
target main article.

### 7.4 Chromium PDF-viewer save

For Chromium's built-in PDF viewer, the visible Save control lives in an
isolated extension webview rather than the publisher page DOM. In external-CDP
mode, AN can select that webview only when its title matches the requested
article, direct its native Save action into a unique bounded staging directory,
and pass the saved bytes through the normal scientific validation pipeline.
The browser must already have legitimate access to and display the PDF; this
path does not solve CAPTCHA, authenticate, or bypass entitlement checks.

### 7.5 Semantic article-PDF control

As a bounded last generic fallback, AN may click one explicit visible
article-PDF control. It does not crawl arbitrary controls. For a small measured
set of publishers (including ACS, Wiley, MDPI, and Nature), AN may derive a
documented article PDF route; those routes are still opened through the
authenticated browser and remain subject to all normal publisher access
controls.

### 7.6 IEEE Xplore page acquisition

`10.1109/` DOIs now use the same public discovery and browser recovery pipeline
as other publishers. The browser opens the discovered article page (or DOI
resolver fallback), clicks a visible PDF control when needed, captures the
download, and applies the normal PDF structure, DOI/title identity, and
document-role checks. No `stamp.jsp` URL is guessed. A failed automatic attempt
can optionally prompt for a locally saved file with `--manual-ieee-fallback`;
`--local-pdf DOI=PATH` still imports a selected file directly.
When the PDF access dialog shows a remembered institution's "Access Through"
control, the browser clicks it, waits five seconds for the institutional state
to settle, closes the dialog if it remains on the article, and retries the PDF
once. A missing institution choice or an actual account login remains an
interactive access step.

[IEEE Xplore's published bot policy](https://ieeexplore.ieee.org/Xplorehelp/overview-of-ieee-xplore/legal-information)
restricts robot/intelligent-agent access. This implementation change does not
alter IEEE's terms or supply entitlement. The separately licensed
[Full-Text Access API](https://developer.ieee.org/docs) remains a distinct route.

## 9. Public API

Install the optional browser capability:

```powershell
python -m pip install -e ".[dev,browser]"
python -m playwright install chromium
```

Basic usage:

```python
from aletheia_nexus.acquire.access import (
    BrowserAccessConfig,
    acquire_full_text_maximized,
)

config = BrowserAccessConfig(
    profile_name="cas",
    channel="chrome",  # optional: use installed Chrome
    headless=False,
)

result = acquire_full_text_maximized(
    "10.1038/s44221-024-00340-4",
    output_dir="downloads",
    browser_config=config,
    unpaywall_email="you@example.com",
)

print(result.status)
print(result.verified_path)
```

For interactive CLI/workflow integration:

```python
def on_interaction(challenge, url):
    print(f"Please complete {challenge.kind} in the opened browser: {url}")


config = BrowserAccessConfig(
    profile_name="cas",
    interaction_callback=on_interaction,
)
```

The callback is notification only. Authentication remains in the visible browser.

## 11. Work budgets

Browser work is bounded by configuration, including:

```text
max source routes
max PDF candidates per route
max authenticated-request redirects
navigation timeout
request timeout
automatic challenge grace period
optional human-interaction timeout (CLI handoff is unbounded when omitted)
poll interval
max PDF bytes
```

v0.5 request/depth budgets remain unchanged.

Broad parallel browser acquisition is intentionally not used. Authenticated
publisher state is sequential and adaptive; parallel tabs would increase
challenge rates, duplicate work and make first-success stopping less predictable.

## 12. Security and privacy

Browser authentication increases capability and therefore increases security
responsibility.

v0.6 rules:

- dedicated browser profile by default;
- official API secret fields excluded from repr/provenance;
- no password/token/cookie/API-key values in acquisition sidecars;
- URL-embedded userinfo credentials are rejected for browser network access and
  removed before persistence;
- literal localhost, `.local`, loopback, private, link-local and other non-global
  IP targets are rejected before browser/API access;
- browser-style ambiguous numeric host forms such as `127.1`, integer IPv4 and
  hexadecimal IPv4 representations are rejected fail-closed;
- page requests are guarded across the persistent BrowserContext, while Service
  Workers remain enabled to preserve real publisher/SSO behavior;
- authenticated API requests disable automatic redirects and revalidate each
  redirect target before following it;
- the final browser navigation URL is checked again before scientific extraction;
- all persisted browser URL query **values** are redacted;
- URL fragments are removed from persisted browser provenance;
- browser profiles must not be committed to Git;
- verified scientific artifacts remain content-hashed;
- browser acquisition never bypasses the v0.5 scientific identity gate.

Browser networking is deliberately compatible with institution-managed VPN/proxy/DNS
environments, so it does not require the local Python DNS resolver to prove that an
ordinary hostname resolves only to globally routable addresses. Doing so would break
legitimate institution-managed DNS and proxy topologies. This means DNS rebinding or a
malicious public hostname that later resolves to a private address remains a residual
risk; v0.6 mitigates it by restricting acquisition to scholarly candidate/derived
routes, validating every explicit URL/redirect, rejecting local and ambiguous numeric
targets, and bounding route expansion. The browser request guard is therefore a
best-effort safety boundary, **not a claim that Chromium is a hardened network
sandbox**.

The local browser profile is sensitive local state and should be protected like a
logged-in browser profile.

## 14. Live acceptance

Use:

```powershell
python scripts/manual_v06_access_acceptance.py
```

For release-quality authenticated acceptance, also provide **Entitled Positive
Controls（已确认有权限的阳性对照）**. These must be papers the researcher has
manually confirmed are downloadable in the **same account, institution, network,
and browser environment** used for the AN run.

A few controls can be supplied directly:

```powershell
python scripts/manual_v06_access_acceptance.py `
  --entitled-doi 10.xxxx/example1 `
  --entitled-doi 10.xxxx/example2
```

For a repeatable freeze run, copy the committed template first:

```powershell
Copy-Item benchmarks/v06_entitled_positive_controls.example.json `
  benchmarks/v06_entitled_positive_controls.local.json
```

Then replace every placeholder with a paper manually confirmed downloadable in
the same access environment. The resulting local JSON corpus has this shape:

```json
[
  {
    "id": "publisher-a-control",
    "doi": "10.xxxx/example1",
    "title": "Manually confirmed downloadable article",
    "access_family": "elsevier-sciencedirect"
  },
  {
    "id": "publisher-b-control",
    "doi": "10.xxxx/example2",
    "title": "Second confirmed article",
    "access_family": "springer-nature"
  },
  {
    "id": "publisher-a-control-2",
    "doi": "10.xxxx/example3",
    "title": "Third confirmed article",
    "access_family": "elsevier-sciencedirect"
  }
]
```

Save it as, for example:

```text
benchmarks/v06_entitled_positive_controls.local.json
```

That filename is git-ignored because it describes one user's current access
environment and is not a universal project benchmark. Run:

```powershell
python scripts/manual_v06_access_acceptance.py `
  --entitled-benchmark benchmarks/v06_entitled_positive_controls.local.json `
  --require-entitled-controls
```

Any supplied entitled control that does not end in `VERIFIED` makes the runner
exit non-zero. With `--require-entitled-controls`, the executable formal
institutional-qualification gate requires all of the following:

```text
stress cases >= 20
entitled controls >= 3
every entitled control has access_family
distinct access families >= 2
all entitled controls = VERIFIED
v0.6-only recoveries >= 1
RUNNER_ERROR = 0
```

Ad-hoc `--entitled-doi` controls are useful for debugging, but a formal qualification
run should use the local JSON corpus so access families are explicit and
auditable. This prevents a misleading release where aggregate acquisition looks
acceptable but AN still cannot exercise access the researcher demonstrably has
or cannot demonstrate any recovery beyond the v0.5 baseline.

By default the runner uses the existing fixed 20-paper corpora:

```text
benchmarks/cdi_acquisition_10.json
benchmarks/seawater_desalination_10.json
```

The live acceptance should be run from the researcher's actual environment with
the intended institutional/account access. The runner keeps one live
`BrowserSession` open across the corpus so a legitimate login/SSO interaction can
benefit later papers in the same batch.

Primary metrics:

```text
stress-corpus v0.5 VERIFIED count / rate
stress-corpus v0.6 VERIFIED count / rate
stress-corpus uplift count
total VERIFIED count
official API recovery count
browser recovery count
v0.6-only recovery count
human-intervention count
challenge-kind distribution
entitlement-required count
entitled positive-control VERIFIED rate
false VERIFIED count = MUST remain 0
```

The stress-corpus metrics are calculated only from the fixed benchmark cohort.
Entitled positive controls are reported separately even when a control DOI
overlaps a stress case. This keeps the v0.5 → v0.6 coverage comparison
comparable to the original 20-paper baseline.

The aggregate 20-paper corpus measures coverage uplift. Entitled positive
controls measure a stricter property: **can AN actually exercise access that is
known to exist?** Both are needed for formal institutional qualification. The
project owner deferred this qualification for the first public v0.6.0 code
release, with the missing evidence explicitly disclosed.

The release target is not a fabricated universal percentage. The meaningful
comparison is **same corpus + same network/institution + v0.5 versus v0.6**.

## 15. Explicit non-goals

v0.6 does not include:

- paywall bypass;
- credential guessing or automated password entry;
- third-party CAPTCHA-solving services;
- stealth browser fingerprint manipulation;
- unbounded crawling;
- publisher-specific guessed PDF URL catalogues;
- Content Parsing;
- OCR;
- RAG / embeddings;
- Knowledge extraction;
- Agent reasoning.

If future real acceptance data shows that a publisher-specific legitimate
adapter is necessary, it should be added only for a measured failure mode with
tests and a clear maintenance owner.

## 16. Exit criteria

### Historical release audit (2026-09-23)

- Local Python 3.11 and 3.14 deterministic suites: 734 passed, 7 skipped on
  each version. The seven real-Chromium access integration cases passed on
  both versions. Ruff, compilation, and dependency consistency checks passed.
- A previously user-acquired IEEE article PDF was imported through the new
  user-operated route, verified as the target main article, and accepted by the
  sequential batch CLI in both explicit-path and interactive-path modes.
- The prior 40-paper live stress run recorded 31/40 VERIFIED. Later independent
  positive controls verified three ScienceDirect papers, two Nature papers, and
  the IEEE paper after user-completed institutional authentication. Thus the
  distinct-paper cumulative result is 37/40, not a fresh single-run rate. The
  remaining papers are `10.1038/nchem.367` and
  `10.1038/s44221-024-00340-4` (explicit purchase/entitlement boundary),
  plus `10.1061/(ASCE)0733-9372(2007)133:11(1004)` (institutional login
  incomplete; entitlement not established). The original 31/40 numerator is
  retained for provenance.
- The user-provided additional 20-paper set reached 19/20 VERIFIED through
  checkpointed AN runs and browser-session reuse. The sole remaining Thieme
  DOI `10.1055/a-2508-9744` reached an institutional SSO path; the user
  confirmed no current subscription. The ACS first-page navigation false
  supplement classification was fixed without weakening article identity checks.
  This historical result used the mixed DOI/title raw input
  `benchmarks/user_20260923_20_with_titles.json`. Future acquisition-layer
  comparisons should use `benchmarks/user_20260923_20_frozen.json`, which fixes
  all 20 titles plus publisher/year; do not transfer 19/20 to that new corpus
  without actually rerunning it. See `benchmarks/README.md` for provenance.
- A later-page DOI alone can no longer validate a downloaded PDF as the target
  article: without a matching first-page title, the DOI must appear on page one.
  This preserves the ACS/Nature title-extraction recoveries while reducing the
  risk of accepting an unrelated article that merely cites the target DOI.
- This audit originally required both final-head hosted CI and a fresh formal
  live run with at least three entitled controls from two access families before
  a stable tag. An IEEE local-file import does not substitute for that automated
  access qualification. On 2026-09-24 the project owner explicitly deferred
  this live qualification for the initial public v0.6.0 code release, while
  retaining final-head hosted CI as a hard code-freeze gate.

The release branch may set its package metadata to `0.6.0` for the final PR
check, but until final-head Python 3.11, Python 3.14, and real-Chromium hosted
jobs all conclude `success`, it must not be merged or tagged as stable
`v0.6.0`. The release notes and README must state that institutional
access has **not** passed formal multi-family positive-control qualification.

The initial public v0.6.0 **code layer** can be frozen when all are true:

1. Python 3.11 and 3.14 deterministic CI is green.
2. Optional Playwright dependency installation, real Chromium startup, and the
   authenticated-session integration smoke test are green.
3. No v0.5 regression.
4. Browser challenge state-machine tests are green.
5. Browser retrieval cannot create false `VERIFIED`.
6. Sensitive authenticated URL values are absent from persisted provenance.
7. Historical real-network observations and known false-positive/false-negative
   cases are accurately documented, without claiming they constitute a fresh
   fixed-corpus or authorized positive-control run.
8. The deferred institutional-qualification gap is conspicuously stated in
   README and GitHub Release notes, and remaining outcomes retain explicit
   categories rather than silent wrong output.

Formal institutional qualification remains a separate follow-up: rerun the
