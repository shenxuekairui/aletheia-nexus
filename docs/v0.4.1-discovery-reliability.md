# v0.4.1 Discovery Reliability & Observability Hardening

> Full-text Discovery（全文发现）可靠性、候选语义与可观测性强化说明。

Aletheia Nexus v0.4.1 不扩展新的 Provider（数据源适配器），而是优先把 OpenAlex + Unpaywall Discovery（发现）能力做成可批量、可追踪、可解释、可测量的稳定基础能力。

## 1. Scope

本阶段完成：

- Retry（重试）与 Exponential Backoff（指数退避）
- Provider（数据源）独立失败隔离
- Provider 级稳定失败状态
- `attempts`（尝试次数）记录
- `elapsed_seconds`（耗时）记录
- Batch Discovery（批量发现）
- DOI 标准化后稳定去重
- `PARTIAL_SUCCESS`（部分成功）语义
- Candidate URL（候选链接）标准化与合法性验证
- Candidate Semantics（候选语义）边界明确化
- `INDEX`（索引）与 `RESOLVER`（解析入口）Host Type
- Acquisition-oriented Ranking（面向获取的优先级排序）
- 自动测试
- 真实网络人工验收与 Benchmark（基准测试）统计
- Metadata Batch（元数据批处理）轻量耗时记录

本阶段刻意不做：

- 新增 Crossref / DataCite / Europe PMC / arXiv / CORE 等 Discovery Provider
- 并发、异步、缓存、复杂限流调度
- PDF 下载
- CARSI / SSO / 浏览器登录
- PDF 文件格式与论文身份验证
- 为 Metadata 与 Discovery 提前抽象共享 Transport / Observability Framework（传输/可观测性框架）

这些边界用于避免在真实需求和瓶颈尚未稳定前提前增加系统复杂度。

## 2. Core pipeline

```text
DOI input
↓
DOI normalization
↓
OpenAlex / Unpaywall
↓
per-provider retry + failure isolation
↓
provider-reported candidate normalization
↓
URL validation
↓
route host refinement
↓
deduplication + provenance merge
↓
acquisition-oriented priority
↓
DiscoveryResult
```

Discovery 回答的是：**哪里可能存在可用全文路径？**

它不回答：**这个 URL 最终是否一定能下载到有效 PDF？**

后一个问题属于 v0.5 Acquisition + Validation（获取与验证）。

## 3. Retry semantics

仅以下暂时性错误自动重试：

```text
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
```

以下错误通常不会因为重复请求自动恢复，因此不重试：

```text
NOT_FOUND
REQUEST_ERROR
PARSE_ERROR
CONFIGURATION_ERROR
```

每个 Provider 独立重试。一个 Provider 失败不会阻断另一个 Provider。

Provider 的 `elapsed_seconds` 覆盖完整操作时间，包括：

```text
HTTP / provider work
+ retries
+ exponential backoff waits
+ provider parsing
```

## 4. Provider status

当前 Provider 级状态：

```text
SUCCESS
NO_CANDIDATES
NOT_FOUND
SKIPPED
CONFIGURATION_ERROR
REQUEST_ERROR
NETWORK_ERROR
RATE_LIMITED
SERVICE_ERROR
PARSE_ERROR
ERROR
```

`ProviderDiscoveryResult` 同时保留：

```text
provider
status
candidates
error
attempts
elapsed_seconds
```

未知编程错误不会被包装为正常业务失败并静默吞掉。

## 5. Batch Discovery

公开入口：

```python
from aletheia_nexus.acquire.discovery import discover_full_text_batch
```

批量层：

```text
原始 DOI 输入
↓
逐条 DOI 标准化
↓
按标准化 DOI 稳定去重
↓
逐篇 Discovery
↓
Provider Retry / Failure Isolation
↓
候选去重与优先级排序
↓
稳定 Batch Status
```

当前 Batch 状态：

```text
SUCCESS
PARTIAL_SUCCESS
NO_CANDIDATES
NOT_FOUND
INVALID_DOI
ERROR
```

`PARTIAL_SUCCESS` 表示：已经得到至少一个有效 Candidate（候选），但同时至少一个 Provider 发生真实失败。

正常 `NO_CANDIDATES` 或未配置 Provider 的 `SKIPPED` 不会误判为部分失败。

Batch 在 v0.4.1 中刻意保持顺序执行。是否引入 Bounded Concurrency（有限并发）必须由真实 Benchmark 的耗时分解决定。

## 6. Candidate semantics

### 6.1 URL type is provider-reported

`CandidateUrlType.PDF` 表示：

> Provider 将该路径报告为 PDF candidate（PDF 候选路径）。

它不表示 Aletheia Nexus 已验证该 URL 的响应一定是 PDF。

例如 Handle resolver（Handle 解析入口）可能被上游数据库放在 `pdf_url` 字段中，但实际访问时仍需要重定向。

以下验证留给 v0.5：

```text
HTTP Content-Type
PDF magic bytes / %PDF header
文件完整性
可解析性
论文身份匹配
```

### 6.2 Version is provider-reported

`published / accepted / submitted` 也是 Provider 报告的 scholarly version（学术版本），不是 AN 已通过文件内容核验后的最终事实。

### 6.3 Host type describes the route

当前 HostType（托管/访问路径类型）：

```text
PUBLISHER   出版社路径
REPOSITORY  全文仓储路径
INDEX       文献索引路径
RESOLVER    标识符解析路径
UNKNOWN     未知
```

v0.4.1 只对真实验收已经证明需要区分的路径做轻量 refinement（细化）：

- `doi.org` / `dx.doi.org` → `RESOLVER`
- `hdl.handle.net` → `RESOLVER`
- PubMed → `INDEX`
- DOAJ → `INDEX`
- PMC → `REPOSITORY`

其他 Publisher / Repository 仍优先相信 Provider 的结构化元数据，不维护庞大的出版社域名硬编码表。

## 7. Deduplication and provenance

相同标准化 URL 来自多个 Provider 时：

- 合并 `provenance`
- 保留优先级更高的主要 Candidate 表示
- 在不冲突时补齐缺失的 `license` / `source_name`
- `is_best` 使用任一 Provider 的正向标记

不会在 Provider 明显冲突时静默推断一个新的论文版本事实。

## 8. Ranking semantics

当前 Ranking（排序）是：

> Acquisition Priority（获取优先级）

回答：**下一步 Acquisition 最值得先尝试哪个路径？**

不是：**哪个 Candidate 是学术上最权威的版本？**

当前优先因素依次包括：

```text
Open Access
↓
provider-reported PDF route
↓
reported scholarly version
↓
route host type
↓
provider best-location signal
```

因此 Repository（仓储）的 OA PDF 可能排在 Publisher（出版社）的正式 Landing Page（落地页）之前。这代表获取便利性，不代表学术权威性更高。

## 9. Runtime observability

v0.4.1 使用 Python 标准库 `time.perf_counter()`，不增加监控依赖。

记录层级：

```text
Discovery Provider
→ attempts
→ elapsed_seconds

Discovery one DOI
→ elapsed_seconds

Discovery Batch item
→ elapsed_seconds

Metadata Batch item
→ elapsed_seconds

Manual benchmark
→ total / mean / median / max
```

刻意不为 DOI 标准化、字符串清洗、排序 key 等微小本地函数逐个计时。

## 10. Real-network benchmark

人工验收脚本：

```powershell
python scripts/manual_discovery_acceptance.py --unpaywall-email "person@example.org" <DOI...>
```

脚本输出：

- Batch Status（批量状态）
- Provider Status（数据源状态）
- attempts（尝试次数）
- Provider elapsed（数据源耗时）
- 单 DOI elapsed（单篇耗时）
- Candidate URL
- URL Type
- Access Type
- Version
- Host Type
- source name
- license
- `is_best`
- Provenance（来源追踪）
- Candidate host/version 分布
- Batch total / mean / median / max
- 各 Provider total / mean / median / max
- Provider elapsed / Batch elapsed 比例

真实网络验收不进入 CI（持续集成），避免外部服务短暂异常造成随机失败。

### Water-electrolysis 10-paper corpus

首轮真实 Benchmark 使用以下 10 篇电解水相关论文，刻意覆盖多个出版社、年代、OA 状态与仓储路径：

```text
10.1126/science.1162018
10.1002/anie.201406668
10.1021/ja510442p
10.1039/C6CS00328A
10.1038/s41560-020-0550-8
10.1039/D0EE04086J
10.1021/acsmaterialslett.4c00699
10.1038/s41467-024-49639-6
10.1016/j.jpowsour.2024.235451
10.1021/acs.chemrev.3c00904
```

初始顺序执行基线：10 篇约 `23.224 s`。这个数字只作为当前真实环境的观察值，不作为性能保证。

该轮真实数据证明：当前首要问题不是盲目增加 Provider，而是先保证 Candidate 语义、运行可观测性与真实 Benchmark 闭环。

## 11. Acceptance criteria

v0.4.1 冻结前要求：

```text
合法 DOI → 多 Provider Discovery
临时 Provider 失败 → 有限 Retry
永久错误 → 不无意义 Retry
单 Provider 失败 → 不拖垮其他 Provider
批量单篇失败 → 不拖垮整个 Batch
所有业务结果 → 稳定状态
Provider → attempts + elapsed + error 可追踪
Candidate URL → 合法、标准化、可去重
Candidate 语义 → 不把未验证信息包装成事实
Host → Publisher / Repository / Index / Resolver 可区分
Ranking → 明确定义为 Acquisition Priority
Benchmark → 能统计 coverage / latency / failures
CI → Python 3.11 / 3.14 全绿
```

## 12. Next decision

v0.4.1 完成后不默认继续堆叠 API。

下一阶段先扩大真实文献集，测量：

- Coverage（覆盖率）
- Latency（耗时）
- Source diversity（来源多样性）
- Provider overlap（来源重叠与互补）
- Failure mode（失败模式）
- Candidate quality（候选质量）

再由数据决定优先做：

```text
新 Provider
或
Bounded Concurrency（有限并发）
或
Ranking 调整
或
进入 v0.5 Acquisition + Validation
```

这保持 Aletheia Nexus 的核心原则：先建立可靠、可验证、可追溯的底层能力，再增加自动化和智能复杂度。
